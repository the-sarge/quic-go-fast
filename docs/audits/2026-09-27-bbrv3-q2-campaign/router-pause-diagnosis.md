## What the measurement means

The frozen model sets `Packet.ScheduledAt` to the original serialization-plus-propagation departure, including when `Advance` runs late. The emitter computes `time.Since(epoch) - ScheduledAt` after `unix.Sendto` completes. Egress lag therefore includes a late model wakeup, delay in the emitter channel/goroutine and time inside the send syscall. It does not separately identify these contributions. The measurement uses Go's monotonic elapsed time; the reported peak timestamp separately uses wall time. There is no 61.44-second S2 scenario event. [The model](../2026-09-25-bbrv3-q1-campaign/model/model.go), [scenario definitions](../2026-09-25-bbrv3-q1-campaign/model/scenarios.go) and [native adapter](../2026-09-25-bbrv3-q1-campaign/router/main_linux.go) remain unchanged.

The existing model tests pass. A private probe importing that exact model confirms a scheduled departure is preserved for injected lateness of zero, exactly 5 ms, 5 ms plus 1 ns and 8.489296 ms. The unchanged boundary passes exactly 5 ms and rejects larger lateness. This verifies the arithmetic and boundary, not reproduction of the historical native pause. There is no correct offline seam here for a regression test of an unknown Linux/Go/VM scheduling cause, so no corrective router patch is justified.

The three failed router receipts report no socket drops, noncanonical packets, send errors, missing timestamps or propagation-storage overflow. Continuation4's maximum ingress delay is below 0.8 ms in both directions despite the egress failure. A simultaneous egress maximum is evidence of a common timing disturbance, but it does not prove a whole-process stop or whole-VM descheduling. Existing five-second `vmstat` samples and one-second router counter samples cannot attribute an eight-millisecond stall. Router sample timestamps come from the ticker and are not a record of actual execution latency. Before/after clock checks remain valid as observed; they do not replace an event-time trace.

## Ranked hypotheses and discriminating observations

1. **Periodic kernel or host work interfering with the gateway.** Prediction: timer/workqueue callbacks, interrupt execution or per-thread scheduling delay coincide with events on a host-specific approximately 61.44-second grid despite process restarts. This best explains the phase pattern, but the responsible task is unobserved.
2. **Go runtime pause or allocator pressure.** Prediction: GC stop-the-world or scheduler records overlap the lag events; changing only the demonstrated runtime cause removes the correlation. Current receipts have no GC trace. Cross-process phase persistence weakens a simple process-age explanation but does not exclude allocation-triggered GC or a runtime response to external interference. GOGC=400 and GOMEMLIMIT=4GiB remain pinned. The inspected local Go 1.27.1 runtime's forced-GC interval is 120 seconds, not 61.44 seconds; that fact alone does not exclude other GC events or prove the guest binary's behavior.
3. **Emitter/syscall or admission-to-emission scheduling delay.** Prediction: a large time interval occurs between original due time, model release, emitter entry and send completion, with no matching GC or kernel-wide pause. The current aggregate maximum includes these intervals, so this remains unresolved. Direct scheduler tracing or thresholded syscall-latency observation is needed before changing queueing or scheduling code.
4. **Deadline or timebase artifact.** Prediction: the supposed overrun arises from resetting the scheduled deadline, including intended propagation, a wall-time step in elapsed-time arithmetic or a scenario event at the observed period. The source and model probe contradict those specific arithmetic explanations. Clock-boundary observations are healthy, but a transient guest monotonic-clock/timekeeping problem cannot be excluded from maxima alone.

There is a concrete kernel-timer candidate to trace, rather than merely a numerically similar interval. [Upstream Linux timer-wheel code at `a243ede718463c7b481878656f1ff32a0ce0fd54`](https://github.com/torvalds/linux/blob/a243ede718463c7b481878656f1ff32a0ce0fd54/kernel/time/timer.c) rounds long timers up to bucket boundaries. A private arithmetic reproduction of its indexing rule yields a recurring 61.44-second interval for 60-second rearming at HZ=100, 250 and 1000 once bucket aligned. [Upstream random-number reseeding at the same revision](https://github.com/torvalds/linux/blob/a243ede718463c7b481878656f1ff32a0ce0fd54/drivers/char/random.c) rearms delayed work after 60 seconds, making `crng_reseed` one specific candidate. Other periodic work can share that cadence. The guest ran Ubuntu `7.0.0-1011-gcp`; its exact timer configuration, reseed events and callback duration were not collected. Upstream source is an explanatory hypothesis, not proof that this guest executed that callback at a peak. Do not disable RNG reseeding, kernel services or security mechanisms on this evidence.
