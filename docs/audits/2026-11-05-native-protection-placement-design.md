# Packet-protection placement design for N3 #1202

**Status:** selected for a local correctness/compiler prototype, not an accepted implementation contract or product qualification. **Date:** 2026-11-05. **Source basis:** retained measured diagnostic `35b83b13a3b94ec3665889c0f6a0844d0f851060`. **Related:** [pipeline redesign](2026-11-05-native-pipeline-redesign.md), [latest measured ECN/writer result](2026-11-05-native-ecn-writer-prototype.md), [comparison input from issue #1232](2026-11-05-send-pipeline-comparison-1232.md). N3 #1202 remains stopped; draft PR #1230 remains held.

## Problem and possible benefit

The latest clean pair reaches 82.744% of baseline goodput at 114.465% of baseline CPU/useful byte. The unchanged targets require about 14.81% more goodput and 3.90% less native CPU/useful byte against that same baseline. Removing notifications and repeated ECN work helped CPU while leaving both targets unmet. Another small helper optimization cannot be presented as the larger repair.

The exact native CPU profile attributes 19.52 sampled seconds to disjoint packet sealing and header-protection subtrees, about 0.21045 estimated ns/useful byte. The underlying XOR-nonce sealing and header-mask application account for 19.24 seconds, about 0.20743 ns/byte. The difference includes wrapper and key-policy work that stays synchronous. Whole connection-loop work is 70.78 sampled seconds and writer work is 29.13 seconds. Moving only pure protection into the existing writer could overlap it with subsequent connection work and reduce the dominant serial path. This is an opportunity estimate from whole-role profiles normalized to window CPU, not an isolated timing experiment or a predicted speedup.

Moving computation does not remove its total CPU cost. Descriptor construction, additional buffer passes, scratch handling and retained key references add work. A more balanced schedule may alter naturally produced GSO buffers and request sizes, but no claim may assume that improvement. A later comparison must report absolute goodput, CPU/useful byte, call geometry, grouping, control latency and retained memory together.

## Alternatives ruled out by current semantics

Deferring registration until an emission batch closes changes the next packet's congestion, pacing, ECN and packet-number observations even when there is no callback. Callback reentry adds further mutable receiver and lifetime boundaries. A facade that still performs all ordered work is not a meaningful pass removal.

A single Linux `sendmmsg` for a group cannot preserve the selected exact member outcomes. After a successful prefix, Linux discards the error from the first failing member; a later retry can return a different error. EMSGSIZE, GSO EIO fallback and other uncertain native errors therefore cannot be reconstructed from the same prefix count. Cancellation opportunities and per-member native-return timestamps also change. The current scalar native adapter remains. See the [documented prefix/error behavior](https://man7.org/linux/man-pages/man2/sendmmsg.2.html).

## Proposed separation

Keep every protocol decision on the connection at its existing observation point: frame selection and serialization, key-phase selection and its callbacks, encryption-limit checks, first-PN and encryption-budget accounting, packet-number commitment, logging, immediate recovery registration and subsequent pacing/ECN decisions. Only a concrete supported transform may be deferred. Capability refusal is side-effect free; once key policy is reserved, synchronous sealing cannot be called as a fallback and count the same packet again.

An opaque handshake-owned protection description captures the exact immutable sending-key generation and header key. It never contains the live updatable sealer, a recovery/preparation view, frame references, a connection callback or permission to look up current keys. Initial scope is concrete non-FIPS ordinary 1-RTT protection. Generic/mock sealers, FIPS policy wrappers, admitted multipath, coalesced/long-header and close/reusable-ciphertext paths keep synchronous protection. AES-128, AES-256 and ChaCha require independently verified immutable underlying primitives; the generic cipher interfaces provide no blanket concurrency guarantee.

The existing native writer uses its own reusable nonce/header scratch, independent of connection scratch. Passing local arrays through cipher interfaces can make them escape once per packet, so a heap-allocation-free transform body must be established from generated code, not inferred from source syntax. The writer invokes no key-policy or logging callback and performs no recovery operation.

## Explicit ownership change

The proposed admitted representation is **committed protection input**, not already completed ciphertext. Header and frame bytes have been copied into an exclusively owned packet buffer, authentication-tag space is reserved in the final wire length, and exact packet/AD/header-sample geometry is fixed. No application or recovery frame can be reread after handoff. The writer may mutate only those owned bytes to produce ciphertext before the first native attempt. Geometry, route, epoch and packet identity remain immutable.

Use a standalone native-only per-buffer plan whose outer construction owner holds the handle directly through callbacks. It names the exact buffer and contains bounded recipes; it is independent of connection completion sidecars and recovery metadata. Callback-driven replacement or early ACK cannot recycle it. An eligible recipe is estimated at 24 bytes on the measured 64-bit target. Two private pools provide a single object with inline storage for one ordinary packet or 67 packet descriptions, estimated at 64 or 1,648 bytes before allocator rounding. Common packet-buffer and recovery-packet layouts do not grow. Exact layout, allocation and synchronization cost must be checked in the prototype; one pool operation per buffer is real added work.

Ownership transfers twice: the buffer constructor transfers the plan into an unadmitted group when it appends the completed member; successful endpoint admission then transfers that group. Capacity refusal retains the staged group and its plans. The constructor consumes and clears its own handle before calling handoff, because handoff can synchronously finish or drop the group and reenter callbacks. Serialization/registration failure and partial-buffer abandonment dispose the exact local plan alongside its buffer. Queued disposal or final native return releases admitted plans before credit callbacks. A claimed plan cannot return to a pool while the writer still borrows it.

The proposed binding check compares the captured sender, request/group identity, buffer and successfully registered token prefix. Existing receiver lookups and registration operations remain at their original points. If binding no longer proves safe deferred handoff, materialize the already-reserved prefix and take the existing ciphertext handoff path, preserving current receiver semantics. A later unsupported packet likewise materializes the prefix synchronously before its ordinary sealing path; policy is never reserved twice. The independent construction/lifetime review accepts this exact fallback at design level; actual source and tests must establish that the handoff implements it.

Active metadata is bounded by existing per-buffer packet limits, request member counts and charged buffer capacity; it adds approximately 4.4% of ordinary-buffer capacity or 8.05% of large-buffer capacity before allocator rounding, plus a native member pointer. These are metadata estimates, not a new payload allowance or admission budget. Cleared pool retention is distinct from active ownership and must be observed in memory measurements.

Queueing committed plaintext extends the reachability of plaintext and old sending keys compared with queueing ciphertext. No traffic secret, connection root or unbounded generation map is needed. Descriptions release key references on safe local/queued disposal or after their transform; a later member can nevertheless retain an old key behind a stalled earlier native call. Claimed storage remains fenced until actual writer return, including cancellation, timeout, fault and connection close.

## Native service and timing

After successful deadline setup, the writer checks current submission permission, protects the next member exactly once, and retains the existing checks before actual native calls and retries. A cancellation during computation can prevent submission; computation alone never creates an uncertain native outcome. EPERM retry and GSO EIO fallback reuse ciphertext and never reapply protection. A failed earlier member leaves later members unsubmitted without requiring their transforms. Existing member timestamps and the final publication fence remain authoritative.

The original absolute deadline already begins with first preparation and already includes synchronous encryption. This change moves encryption into claimed writer service and the native borrow; it does not create or extend a budget. The unchanged deadline and watchdog cutoff still apply. Service time, shared-writer scheduling, expiry and control latency can change and must be observed. Independent endpoint control continues to progress while protection or native I/O is in flight.

## Useful small improvement retained

Source `2dabc2cbdd5a6e6ad8eb471e3fda3d72cf5f53e1` adds only a canonical-registration first-initialization cleanup to measured source `35b83b13a3b94ec3665889c0f6a0844d0f851060`. Every issued registration slot is already zeroed and is never reused. Assigning the four initialized fields removes a redundant full-record clear while preserving required pointer barriers. Exact Linux generated code shrinks from 130 to 112 instructions and a 72-byte to a 40-byte frame; four zero stores and `runtime.wbZero` disappear. Nineteen other available common/native bodies normalize identically; an absent standalone symbol is excluded.

Existing lifetime characterizations pass on baseline, temporary changed source and the owned worktree; fourteen independent identity/compiler checks pass. Sixty-one evidence files and a manifest are preserved under `canonical-first-initialization-local-validation/` in the existing issue #1202 diagnostic archive. This head is explicitly unmeasured. No standalone remote performance run was added and instruction counts are not treated as measured CPU savings.
