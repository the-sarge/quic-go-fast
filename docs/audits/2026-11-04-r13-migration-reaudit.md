The binding rule makes a newly discovered shared-state effect a slice stop until a scoped re-audit establishes that it fits the existing outcome and one-PR budget. These effects are that case. None changes an owner: each extends a seam R9, R10 or R12 introduced, with the sender's change serving the endpoint's existing per-transport grant.

The [issue comment on #1033](https://github.com/the-sarge/quic-go-fast/issues/1033) carries six findings deferred from R9. Each is dispositioned here against the source: C-002 (target refusal after an ID is consumed), C-004 (a validated tuple keeps no CID), C-005 (tuple identity), C-006 (a failed candidate's spare CID is never retired) and C-007 (tokens only on the original runner) are required by this design. C-003 (a retired candidate CID stalls retries until the deadline) stays failing safe, costs only a local re-pick at the candidate's probe, and is folded in because a cutover must not activate a retired CID anyway.

## Accepted design

Keep child #1033, its private typed domain and one independently green product PR. No exported method, new platform, controller formula, wire format, worker or persisted state enters the slice. The plan's R13 section states the design as the current contract. The reasoning that doesn't belong in a contract follows.

**Nil stays path zero's current tuple.** R10 kept the nil route so ordinary connections pay nothing, and R12 rejected giving path zero a route value. Everything that reads the nil branch already means "path zero, wherever it is now": the packer's context and destination CID, `c.mtuDiscoverer`, `c.conn`, close and `LocalAddr`. So a path-zero cutover moves the sender's fields, as `replacePath` does, except that it doesn't call `reset`, whose generation cancel would disturb other paths. What actually changes is one distinction the code has been able to skip until now: a member's nil transport means the connection's own transport, and that is no longer the sender's primary once path zero moves. An explicit origin reference separates the two.

**One reservation record.** A retained generation and an aborted attempt have the same release condition: a time has passed and an epoch has resolved. A generation has a retention expiry and an already resolved fence, and an abort has no retention and a possibly unresolved fence. One list with one release path gives the plan's paper trace directly, including that a canceled candidate never frees an older unit.

**The fence comes after validation.** The old epoch is revoked only once the candidate has validated, so the old tuple keeps working for the whole validation, and a failed or canceled validation costs nothing. Cancellation during the fence can still win, since the caller's outcome is decided by the same compare-and-swap R9 uses. The old tuple then gets a fresh epoch. Revoked requests return as unsubmitted, and reliable work returns through its ordinary owner.

**A fencing path keeps the primary.** It stops being offered to the scheduler but stays primary-eligible, because local capacity and a brief local operation must not move the pointer. Ordinary work is held, as it is with no primary in view, and a survivor keeps carrying ACKs and recovery. Only with no survivor does a path-zero fence hard-block like a retired zero, so no ACK-only packet is packed against a revoked epoch. It still counts for DATAGRAM placement: [PR #1162](https://github.com/the-sarge/quic-go-fast/pull/1162) merged during this audit, and `placeDatagram` with no views drops every queued frame, so hiding a lone fencing path there would discard DATAGRAMs that fit.

**Captured callbacks.** A census of what a transport can do to a connection after its map lookup found three. `Transport.close` sets `transportClosed` under the mutex before snapshotting, so testing that flag in the same critical section as the removal makes close and detach strictly ordered. A stateless reset's `destroy` runs after the lookup, so it is counted under the mutex while captured, and a nonzero count refuses detachment. A captured `handlePacket` only queues a packet. Its response follows the current route rather than this transport, and the one way it can end the connection is a valid stateless reset token, which only the peer holds and which ends the connection on any socket. That is the peer's authority, not this transport's lifetime, so it gets no fence, which also keeps the receive path unchanged. `ReplaceWithClosed` is called only by the connection goroutine through `connRunners`, which loses the runner at publication.

**Server cutover trigger.** RFC 9000 §9.3 and the existing ordinary code switch only on the highest-numbered non-probing packet, and this keeps that rule per path. The unit is reserved at that trigger, not at validation, because a peer may probe a tuple and never move to it.

**Declared seams.** A primary endpoint fault stays fatal and closes through a survivor, as [R14](https://github.com/the-sarge/quic-go-fast/pull/1169) ships it. R14's re-audit left path-level continuation to R13, but R13's contract never listed it, and its author confirmed the clause wasn't a checked assignment. The owner decided on 2026-11-04 that continuation becomes a separate slice before public enablement, now [R20](../adr/2026-10-24-multipath-reno-plan.md#r20). R14 reads a nil member transport as the original runner and `closeUsable(nil)` as the primary endpoint, so both follow the origin reference. Peer-created server paths don't migrate locally. Public `MigrateV1`, `WaitTransportDetachedV1`, `PathsV1` state and sentinel mapping beyond the private drivers stay with R16.

**Outbound resets.** Removing routes creates an effect the census above doesn't cover: the transport then treats a live CID as unknown. If its reset key is the one that issued that CID, its stateless reset is valid and ends the peer's connection. A sticky mark on the keyed transport stops all its resets, which are best effort, and needs no per-CID state. Its one cost is that another connection's peer on that transport waits for its idle timeout rather than getting a reset. A key shared with a transport this connection never attached stays the existing multi-instance contract.

**ECN.** Two review rounds found three distinct failures in clearing the native evidence's failed latch at cutover: tracker state and testing length, deleted submission evidence, and CE counts that a failure never recorded. Three at one owner triggered the approach stop, so the design stopped patching that restart. A path whose evidence has failed stays failed across cutover, and only a healthy tracker restarts, from baselines. The cost is that a new tuple doesn't mark after a failure on the old one, which RFC 9000 permits, since revalidation is optional and Reno's loss response is unaffected. Exact attribution of a counter increase to a generation isn't available from cumulative counters, so early certification is allowed, and it corrects itself because capable state keeps checking.

## Rejected alternatives

Giving path zero a route value once it moves would keep the sender's fields fixed, but every zero-specific read in `selectRoute`, `placeDatagram`, `pmtuObservation`, `notePMTU` and close would then need a second branch, and the origin's fault would still need the same fix at detachment. Calling `replacePath` as it stands would cancel other paths' queued work through the sender-wide generation. Fencing before validation would stop the old tuple for a whole validation and turn every failed attempt into an outage. Fencing every captured `handlePacket` would add a second lock per packet for no reachable harm. Scanning a transport's whole handler map at detachment would hold its mutex for a time proportional to its other connections, so the connection supplies its own CIDs and tokens. Sizing a new attachment table for retained generations would duplicate the four-unit pool. Per-CID reset tombstones would grow with every detached transport for the connection's life and miss later-issued CIDs. Reconciling the native evidence so a failed path can restart would rebuild a ledger the failure deliberately discarded, with no way to prove an uncertain write was accepted. Each is rejected on merit.
