## Ranked hypotheses and discriminating measurements

1. Additional per-packet registration, recovery and completion work limits the connection owner: compare same-binary CPU profiles and exact registration/completion counters; change only the PTO fold implementation.
2. Execution handoffs leave ready native work idle: measure enqueue, claim, native start/return, reconciliation and consumption boundaries; inspect execution states; vary writer reconciliation, progress wakeups, producer yielding and dispatch placement separately.
3. Smaller effective batches amplify native calls: count request bytes, datagrams and native call bytes on both routes.
4. Capacity or protocol eligibility throttles production: count refusal reasons and stop reasons; enlarge only the per-connection retained-record capacity as a diagnostic, preserving the other limits.

Instrumentation commit `ecbb35a364343f9c33b92d72389ae6ef4f7bb8d1` adds window-gated scalar counters and every-128th-operation timing samples. It changes no production policy. ## Execution trace: which owner is late

Trace-only commit `2f021945a48a75033cd5be3601a10db2398a9035` adds a 100 ms server execution trace one second into the measurement window. It preserves the instrumented control's policy. Keyed stream/write events identify data installation, the first return opportunity, application wake and mutex reacquisition; native connection/registration IDs identify enqueue and native start/return. Regions identify connection send, receive, completion and application write. Logging and formatting occur inside some locks: use the trace for ordering and ownership, not as an untraced latency estimate. The captured interval is 100.178 ms; parser transition checks reported no inconsistency. Boundary-censored events remain censored.

The native writer is Runnable for 57.960 ms, Running for 5.585 ms and in Syscall for 19.231 ms. Connection-originated wakeups account for 56.930 ms of writer runnable time; independent-progress wakeups account for 0.986 ms. Mean runnable delay is 36.53 µs from connection `prepare`, 36.85 µs from `take`, 28.33 µs from `submit`, and 0.497 µs from independent progress. At least one Go P is explicitly Idle during 92.65% of writer Runnable time. This rules against all Go execution slots being continuously occupied; it does not prove physical CPU availability or expose OS scheduling.

The nominally unqueued gaps average 54.65 µs, but split into 21.59 µs before enqueue and 33.06 µs after enqueue. Before enqueue, the connection is Running for 92.8% of the interval and the application is predominantly waiting for its existing write to drain. After enqueue, the writer is Runnable for 97.6% of the interval. Application mutex reacquisition averages 0.15 µs and completed-write-to-next-install 0.41 µs. The application also suffers runnable delay after a return opportunity, but neither its own loop nor stream-mutex contention explains the main gap.

In a representative interval at trace-relative 44.240–44.297 ms, the writer returns, the connection completes recovery and starts packing, the next request is enqueued at 44.266 ms, and the writer remains Runnable for another 30.27 µs while connection receive/send work continues. The application's current data was installed before this interval. Channel `runnext` replacement and work-steal behavior in the local Go 1.27.3 runtime are plausible mechanisms, but the trace does not expose queue placement or prove particular backoff sleeps. The controlled producer-yield and dispatch experiments establish scheduling sensitivity without turning that implementation hypothesis into fact.

## Recovery work still requiring design, not speculative prerequisites

`internal/ackhandler/local_completion.go:169–207` creates and consumes a per-packet registration identity; accepted/uncertain completion re-evaluates loss and the timer at lines 230–236. `sent_packet_history.go:359–364` searches/deletes packet-distance qualifications. `local_ecn.go:195–200` inserts pending singleton evidence and lines 256–299 complete/coalesce it, including suffix-moving deletions. `settleLocalUndo` runs at registration and completion. Profiles measure these stacks, but do not prove a specific replacement. The Reno fixture has no rich congestion dispatcher; its immediate-return rich-completion path is not the leading cause.

The next design must preserve ordered per-packet facts and connection-owned recovery policy while avoiding derived work whose result is unused between facts, and must preserve overlap between production and native service. A bounded batch-completion or transaction design requires a semantic audit of callbacks, pending/higher-ACK behavior, timer observability, ECN, path identity and failure classes before adoption. It is not authorized as an implementation by this diagnosis. Do not replace the stopped N3 contract with “optimize until it passes,” split out a cache solely because its local correctness is easy to prove, or weaken the product thresholds.
