D1 accepts the runtime improvement: `HandleDatagramFrame` checks capacity under `rcvMx` before allocating/copying admitted data. Full-queue logging remains outside the lock and notification remains inside the admitted branch. No queue, API, ownership, parser, send-path or dependency change is included. Contract closure is not triggered under the accepted plan.

The comparison base is `ca74423b6517bf5aed9e5230110f6da6f3cc7126`; the candidate code is `fd9b1136fed49f06952f26d92b46d043da151300`. ## Finite benchmark receipt

Environment: Go 1.27.0, darwin/arm64, Apple M4 Max, `GOMAXPROCS=4`, debug logging explicitly disabled. Each case uses a preallocated 1071-byte frame and warms queue admission/drain once. SteadyDrain measures one admission/removal; BurstDrain measures 128 admissions followed by 128 removals; Overflow measures one dropped frame with a prefilled queue. Exactly one base/candidate pair was run, with 10 samples of 200 ms per case. No replacement, physical network, platform sweep or profiler was used.

Command: `GOMAXPROCS=4 go test -run '^$' -bench '^BenchmarkDatagramReceive' -benchmem -count=10 -benchtime=200ms`. Comparison used the already cached `golang.org/x/perf` benchstat version `v0.0.0-20260825160852-19be9d8e6c70`.

| Workload | Base ns/op | Candidate ns/op | Timing comparison | Base → candidate B/op | Base → candidate allocs/op |
| --- | ---: | ---: | --- | ---: | ---: |
| SteadyDrain | 144.4 | 133.2 | -7.72%, p=0.000; not an attributable improvement | 1176 → 1176 | 1 → 1 |
| BurstDrain (128 messages/op) | 18640 | 17770 | statistically unchanged, p=0.190 | 153600 → 153600 | 130 → 130 |
| Overflow | 136.750 | 2.948 | -97.84%, p=0.000 | 1152 → 0 | 1 → 0 |

The base first-five to last-five sample means increase by 7.1% for SteadyDrain, 11.8% for BurstDrain, and 16.0% for Overflow; the candidate does not show the same upward drift. This base-side drift biases the preserved-case comparison toward the candidate and weakens timing confidence. No >5% timing regression was observed in this pair, with that qualification; the SteadyDrain difference is not an attributable improvement. These samples do not establish host contention or a concealed regression, so no replacement pair was run.

Allocation counters establish the eliminated dropped-message allocation independently of timing variability. Source placement establishes that dropped frames also skip the payload copy. These results characterize this host/workload only and make no application throughput or metadata-allocation improvement claim.

## Regression evidence

`TestDatagramReceiveOverflowNoAllocation` failed before the runtime patch with 1 allocation per drop and passed after it with zero. The four new logical cases cover overflow allocation, capacity-plus-one FIFO/drain and empty readmission, input-buffer reuse and returned-payload retention, and bounded concurrent production/draining. Existing blocking, cancellation and close tests remain in place. No guard mutation or new maintained verification tool is required.

Focused checks passed: `go test -count=1 -run 'TestDatagram' .`, `go test -race -count=1 -run 'TestDatagram' .`, and `go test -count=1 ./internal/utils/ringbuffer`. Final reviewed-head whole-suite certification and hosted-check availability are recorded in the product PR; this receipt does not predict those results. Review budget: one initial review and at most one replacement. No accepted untraced production consumer remains; physical application integration stays externally owned.
