# Issue #46: randomized-corruption Dial timeout

**Disposition: historical cause unresolved; a constructed corruption/recovery mechanism reproduces the same Dial error. No production or active test change.** Four instrumented random executions passed; none reproduced the timeout. A fixed eleven-Handshake replacement schedule caused `context deadline exceeded` at the unchanged one-second Dial deadline, with successful direct writes, checksum-correlated authentication drops and continuing recovery. Its no-op control completed Dial and transfer. This does not attribute the historical failures to that schedule, establish a regression, or resolve [issue #46](https://github.com/the-sarge/quic-go-fast/issues/46).

## What the traces establish

[summary.json](summary.json) contains derived counts, timing and per-selection receiver events. [summarize.py](summarize.py) regenerates it from the six `raw/<case>.jsonl` files without executing tests; it checks contiguous callback order and successful qlog encoding. All recorded replacement writes in all six cases returned the full datagram length without error. A completed UDP write alone does not establish receipt.

M1, M2 and L1 did not select handshake corruption before Dial returned. They exercise instrumentation and later transfer corruption but do not discriminate among the timeout hypotheses. L2 selected outgoing datagrams 4, 6, 7 and 11 before Dial completion. Each mutation lies within a Handshake packet, each direct write succeeded, and each replacement checksum appears in a client `payload_decrypt_error` event. Server PTO expiry events occur at 66.530 and 174.510 ms from capture start. Unselected datagram 10 carries a usable Handshake packet; Dial returns at 185.606 ms from capture start. This supports recoverable handshake delay for that captured sequence, not an observed recovery failure.

F1 is a **constructed mechanism**, not a replay. Its eleven successful replacement writes correspond to eleven client Handshake authentication drops. Server Handshake PTO expirations occur at 23.700, 61.712, 137.285, 287.411 and 586.610 ms from capture start. The final server Handshake timer is set for 1182.923 ms, after the context deadline at 1000.466 ms. Dial reports `context deadline exceeded` at 1001.025 ms. Client Initial traffic and server ACK activity continue in the trace; the evidence does not show a stopped recovery loop. Initial RTT/PTO initialization and exponential scaling are visible in `internal/utils/rtt_stats.go` and `internal/ackhandler/sent_packet_handler.go`; the recorded retry sequence is consistent with those paths.

F2 delivers the selected Handshake datagram unchanged through the same direct endpoint socket write and suppresses normal forwarding. The client initially buffers it pending keys, then records successful Handshake and coalesced 1-RTT packet receipt. Dial and all original transfer assertions pass. It is a matched selection/path control, not byte-for-byte or timing-identical replay: successful TLS completion means only one Handshake datagram reaches the selection rule. Together F1/F2 demonstrate that byte damage can outlast this deadline without requiring failed writes or a stalled recovery loop. Neither excludes those alternatives in an uncaptured historical occurrence.

## Datagram, path and observer limitations

The callback receives **UDP datagrams**, sometimes containing several QUIC packets. The retained `parts` lengths/types describe the original datagram before mutation. L2's datagram 4 contains a Handshake packet and a trailing short-header packet; its mutation damages the Handshake packet, not necessarily every coalesced packet. Receiver events share a datagram checksum and must not be counted as multiple corrupted datagrams. CRC32c is a correlation aid, not a collision-free identity; direction, time, length and packet boundaries provide additional context.

Normal forwarding uses the proxy sockets and queues after `DropCallback` returns false, applying `rtt/2` delay. Selected replacements write synchronously from the server transport directly to the client's socket and return true, bypassing both proxy forwarding and its added delay. They arrive from the server address instead of the proxy address. Callback `from`/`to` fields describe the observed original path; `dial_start` identifies the endpoint and proxy addresses, from which the direct-send path is known. F1/F2 retain this distinction. Endpoint checksum events confirm relevant receipt; actual proxy socket-write completion times/results were not instrumented, so absence of such an event would not alone locate a forwarding failure.

[instrumentation.patch](instrumentation.patch) retains the random instrumentation against the pinned source; [mechanism.patch](mechanism.patch) independently retains the F1/F2 variant against the same source. They are alternatives, not cumulative patches. Both pass `git apply --check` on the final source. The random patch keeps one selection draw with bound 4 or 20, and only then offset/replacement draws, preserving the original 25% long-header and 5% short-header distribution, possible no-op byte replacement, direction and direct-send/drop behavior. It does not correct the original misleading 20% comment. F1/F2 deliberately substitute a fixed diagnostic selection and replacement rule, as declared in the ledger; neither schedule is installed in active tests.

Instrumentation retains decisions, old/new bytes and offsets, datagram order/length/checksums/boundaries, callback/write timings, write results and endpoint qlog events in memory, then serializes at cleanup. Trace events use one shared relative clock. Allocations, serialization, checksum work, clock reads and a mutex add observer effects and can change scheduling. Record timestamps/order are observation data, not a total causal order. No extra corruption random draws were added, but instrumentation can affect interleaving with unrelated random users. TLS bytes, packetization and live UDP timing are not reproduced by a test-shuffle seed. The capture is not a raw encrypted-payload archive. Active Go files were restored exactly; only audit artifacts remain in the final change.

## Proposed next decision

Do not ship a transport fix, extend deadlines, change corruption probabilities, quarantine the test, or close the issue on this evidence. H1 is demonstrated as a possible mechanism; H2 and H3 remain unresolved for the historical failures. No narrowly justified production patch or historical regression-test contract is available yet.

The smallest useful next investigation is to capture a **naturally scheduled matching failure**, rather than manufacture more passing attempts. Proposed observation window: at most **ten ordinary Linux Go 1.27 race/GSO-disabled self-test invocations at scale 3**, no dedicated reruns, stopping at the first matching Dial timeout or after the tenth invocation. Retain this decision/write/endpoint capture and add actual proxy-forward socket-write timing/results, so successful delivery followed by authentication rejection/PTO can be distinguished from failed forwarding or missing recovery. Publish all invocation outcomes even if no failure occurs. This proposed window is not started by this report and needs an accepted implementation/observation decision; the offered diagnostic budget flexibility has not been used to install instrumentation in routine CI.

For a captured failure, the discriminating contract is: bind its exact selection schedule and QUIC packet boundaries to replacement and proxy-write outcomes, receiver drops/ACKs, outstanding Handshake data, PTO deadlines and Dial expiry. Only then propose a fix and a regression at the demonstrated seam. A constructed replay must document any packetization/timing mismatch and must not be promoted to a historical cause merely because it times out.
