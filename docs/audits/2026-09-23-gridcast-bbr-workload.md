# GridCast workload for opt-in BBRv3 planning

This investigation supports [Characterize GridCast’s WAN bulk-transfer workload](https://github.com/the-sarge/quic-go-fast/issues/553), under [Design opt-in BBRv3 for GridCast bulk transfers](https://github.com/the-sarge/quic-go-fast/issues/552). It characterizes the existing consumer and proposes a representative workload; it does not select performance thresholds, the BBR algorithm baseline, an API design or consumer implementation changes.

## Finding and evidence boundary

The representative consumer is a receiver-authorized, block-pipelined file transfer over a wiremux QUIC connection, normally sending 1,024-byte source and repair Symbols as DATAGRAMs while retaining a reliable control stream. Its offered load can stop for source reads, encoding, receiver admission, verification, feedback and migration. Treating it as an always-backlogged fixed-rate DATAGRAM generator would miss these application limits. The source trace and qualifications below are the basis for that conclusion.

Read-only inspection pinned GridCast to `d852c9b0958004a0b235d896332d96958731b0ca`, its selected wiremux dependency to `7566390c41ebe79315b29fffcea5c564cae5c20f`, and the quic-go-fast planning checkout to `c9e687e4ebad69bb9f53e78aae7566d06006b722`. GridCast's `go.mod` requires wiremux `v0.2.4-0.20260922175107-7566390c41eb`, codemux `v0.5.1`, Wellspring `v0.6.0`, and upstream module identity `github.com/quic-go/quic-go v0.62.0`, replaced in the main module by `github.com/the-sarge/quic-go-fast v0.62.1-fast.3`. The latter tag resolves locally to `81b06388832a97d51af5bc408d27ca6c47eb66a9`; it is distinct from the planning checkout. This is declared source selection, not inspection of a deployed binary's module metadata. [GridCast module][gridcast-module], [wiremux module][wiremux-module], [fork release revision][fork-release].

Source links are immutable commit links. GridCast and GridSwarm links may require repository access. No consumer checkout was modified, no benchmark was run, and no new production trace was collected. Search covered production connection/options code, Symbol delivery and scheduling, Store capacity/verification, progress reporting, release decisions and retained measurement documentation. Absence claims below are limited to those pinned sources.

## Deployment information

**Operator-supplied, 2026-09-23:** “macos/arm64, linux/amd64, and windows/amd64 are probably the most important.” Bandwidth, RTT and loss “will all vary widely.” File sizes are expected to be mostly large, with “10GiB to 50GiB” offered as a range estimate. These are tentative deployment priorities and estimates from the live investigation, to be preserved in the ticket resolution; they are not a selected acceptance matrix. Concurrency counts, quantitative path distributions and operational trace locations were not supplied.

**Code/document-proven support:** GridCast's release workflow builds Linux amd64/arm64, macOS amd64/arm64 and Windows amd64. Its release decision narrows Linux to GNU/glibc and Windows to Windows 11 24H2+ on NTFS and Server 2022/2025 on NTFS or qualified ReFS. Windows arm64 is not a release cell; FreeBSD/OpenBSD lack certified native codec artifacts. Release support is not evidence that every cell is an initial WAN qualification target. [Release matrix][release-matrix], [release decision][release-decision].

**Historical operator context:** the earlier quic-go-fast emission deployment budget names four dedicated physical cores/four Go processors per endpoint and rejects two-core relevance for that experiment. That is a separate performance contract, not a newly established BBR host budget. Reconfirm CPU, NIC, storage and virtualization constraints before setting this effort's limits. [Prior deployment budget][deployment-budget].

## Actual transport and ownership path

Initial pairing obtains the invitation's codemux authenticator, then calls `wiremux.Dial`; Symbol data does not pass through a separate codemux bulk-data API. Resume authenticates a fresh carrier and calls `wiremux.EstablishAuthenticated`. GridCast's migration similarly establishes a candidate through wiremux and substitutes a fresh authenticated Attempt. The application-facing interface retains reliable I/O and optionally borrows `Datagrams()` from either `Wire` or `ManagedWire`. [Initial pairing][pairing], [resume establishment][resume], [migration authentication][migration-auth], [Symbol delivery][symbol-delivery].

The default wiremux upgrade plan selects its built-in `quic.Transport{}`. That transport creates a `quicgo.Transport`, configures client/server QUIC settings, dials or listens, and exposes one bidirectional stream: the client disallows incoming streams, the server allows one, and both disallow incoming unidirectional streams. The same connection exposes the optional DATAGRAM carrier after negotiation. These are transport roles, not necessarily GridCast Sender/Receiver roles. [Upgrade plan][upgrade-plan], [QUIC adapter][quic-adapter].

GridCast has no production `NewManagedPacketEndpoint`/`WithManagedPacketEndpoint` call in this revision. `ManagedWire` denotes authenticated establishment and lifetime, not a reusable managed UDP endpoint. Ordinary eligible wiremux-owned native sockets receive an exact-resource permission; `adapter.NewQUICTransport` wraps the selected peer and registers `ConfigureExternalPacketIOV1`, including the checked batch writer and explicit receive-format permission. Its separate lease branch invokes `ConfigureManagedPacketIOV1` only when an actual managed lease receipt exists. Controller selection must preserve both contracts rather than equating them. [GridCast adoption boundary][adoption], [permission issuance][upgrade-plan], [packet binding][packet-binding], [managed endpoint][managed-endpoint].

The direct profile initially uses 1,232-byte UDP payloads, retains path-MTU discovery, and offers `wiremux-quic/2` with DATAGRAM support before legacy `/1`. Its lower DATAGRAM payload ceiling is 1,192 bytes; the root wiremux envelope consumes one byte, leaving 1,191 application bytes. The pinned library also implements an exclusive TURN `/3` profile with fixed 1,200-byte packets, disabled path-MTU discovery and a 1,159-byte public DATAGRAM ceiling. **That is library capability, not current GridCast deployment:** wiremux requires explicit `WithTURN`; the pinned GridCast production option construction has no TURN configuration. Current ordinary relay fallback is therefore a reliable carrier outside the direct QUIC BBR comparison. Record the actual selected topology in every measurement. [Packet profiles][quic-adapter], [root DATAGRAM framing][wire-datagrams], [TURN opt-in][wire-options], [GridCast options][gridcast-options].

## Application traffic, scheduling and backpressure

| Property | Observed behavior and evidence |
| --- | --- |
| Content geometry | Canonical nonterminal Blocks contain 8,192 Symbols × 1,024 bytes = 8 MiB. Manifest policy permits up to 50,000 file rows and 131,072 source Blocks; these are limits, not observed file distributions. [Manifest geometry][manifest] |
| Record size | V4 Symbol identity/framing costs 75 bytes, so a full Symbol record is 1,099 bytes. Wiremux adds its one-byte envelope, producing 1,100 bytes passed to QUIC's DATAGRAM API before QUIC framing/protection and UDP/IP overhead. Both library ceilings fit it. [Symbol record][symbol-record], [root DATAGRAM framing][wire-datagrams] |
| DATAGRAM eligibility | `activeTransfer.datagramEnabled` requires the initial Block pipeline plus an authenticated native plane large enough for a maximum Symbol record. `SendDatagram` promises local admission only. Reliable source delivery remains available when that plane is absent/too small or the scheduling policy falls back. [Symbol delivery][symbol-delivery], [scheduler][datagram-schedule] |
| Reliable traffic | The control channel carries scheduling, inventory, verification, migration and completion records. Reliable fallback uses Symbol frames batched to a 64 KiB byte budget; batches do not cross Blocks and flush before peer waits. Both control and reliable Symbols share the Wire stream rather than independent QUIC streams per Block. [Scheduler][sender-scheduler], [batch framing][batch], [control ownership][symbol-delivery] |
| Sender concurrency | A single owner walks source rows/Blocks, digest-checking source bytes before deriving Symbols. The default 137 MiB Sender reservation supports eight held full source Blocks; explicit budgets below 74 MiB cannot enable repair generation, and reliable-only operation extends down to 9 MiB. Receiver grants and negotiated limits can reduce usable concurrency. [Sender working budget][sender-budget], [scheduler][sender-scheduler] |
| Receiver concurrency | Defaults are six collection slots and two completion workers under a 1 GiB reservation. These are conservative accounting reservations, not process RSS limits or six connections. Budgets can change admission/worker capacity. [Store defaults][store], [receiver working budget][receiver-budget] |
| Burst shape | One DATAGRAM scheduler turn visits each held eligible Block in order and attempts up to 64 fresh ESIs, source-first and then repair. It polls evidence before each emission and stops on pause/fallback/retirement. There is no fixed Mbps offered-load parameter in this scheduler; actual bursts depend on feedback, codecs and bounded queues. [DATAGRAM scheduler][datagram-schedule] |
| Repair authority | Receiver authority is an absolute ESI interval backed by reserved capacity. Initial allowance is up to K+16, normal capacity K+128, and maximum K+512, bounded by actual reservations. Subsequent authority extensions are at most 64 per turn. Insufficient populations can expand to the maximum; exhaustion or ESI exhaustion selects reliable source fallback. This is adaptive bounded redundancy, not a constant FEC percentage. [Store authorization][datagram-authority] |
| Pause and feedback | Default bounded repair pauses new authority during decode; explicit continuous mode permits repairs within the separately bounded 256 KiB incoming reserve. Decode success pauses both modes before later checking/staging finishes. Feedback occurs at 64-arrival checkpoints or a pending scheduling transition; exhausted authority can be replaced only after the appropriate progress/boundary conditions. The repair timer is `max(2s, IOTimeout/4)`, hence 30s at the default two-minute control-step timeout. [Repair mode][repair-mode], [authorization][datagram-authority], [scheduling/retirement][datagram-schedule], [retirement conditions][datagram-retirement], [control timeout][activation] |
| Queue backpressure | Wiremux root and native QUIC adapter each have eight-entry admission queues; they eventually call quic-go `SendDatagram`. GridCast's receiving goroutine feeds a one-entry channel into the control owner. Queue admission, QUIC acknowledgment, retained evidence and verified content are distinct boundaries. [Root queue][wire-datagrams], [native queue][quic-adapter], [receiver loop][datagram-schedule] |

Consequently, a sustained large Transfer can be intermittently application-limited even when the network has spare capacity: waiting for Block grants, a free held-source slot, fresh repair authority, storage/codec work, source hashing or a migration barrier can all withhold new data. This is an inference from the cited scheduler and Store transitions, not a measurement of their frequency. The default wiremux transport also emits keepalives every 15 seconds with a 30-second idle timeout; those keepalive packets do not imply useful application activity. [Sender waits/barriers][sender-scheduler], [transport idle defaults][quic-adapter].

A Transfer can span successive Attempts, and a single Attempt can contain multiple active Blocks. Neither implies multiple concurrent QUIC data connections. GridCast's “Path migration” means a relay-backed Attempt is replaced by a fresh authenticated direct Attempt, with probing before cutover; it is different from quic-go's same-connection `MigratedPath` state reset. Multiple user processes/Transfers can contend, but their operational count remains unknown. [GridCast vocabulary][gridcast-context], [migration owner][migration], [Sender attempt][sender-attempt].

## Measuring useful delivery

The existing CLI payload counter is unsuitable as the acceptance numerator. It includes repeated payload and can exceed file size; the Sender counts DATAGRAM admission, while the Receiver observes arrived payload after Store admission handling. Its displayed rate uses five one-second buckets including the current partial second and is scoped to a connection generation. It excludes headers but does not exclude all redundancy or prove publication. [CLI activity][progress], [DATAGRAM observations][datagram-schedule].

The Store exposes a stronger intermediate observation: `VerificationProgress.ConfirmedBytes` sums each confirmed Block's actual `TransferLength` once and removes credit if confirmation is withdrawn. Saved evidence awaiting re-proof receives no credit. This can supply logical verified-byte progress, but cached/restored content can create verification progress without equivalent new network delivery. Receiver reports of this value at the Sender are explicitly display-only and do not themselves update `BlockVerified` or meaningful-progress authority. [Verification projection][verification], [peer progress][verified-progress].

**Proposed measurement definition, not yet accepted:** measure newly useful unique logical file bytes for the run over a declared monotonic interval. For a fresh empty-destination transfer without reusable evidence, the completed numerator is the sum of regular-file manifest lengths; require destination publication and independent content verification. Use a receiver-local end-to-end interval from admitted application transfer work through successful publication as the primary candidate, and separately record admission-to-all-verified and Sender-observed completion intervals to attribute storage/finalization/control delay. Do not silently exclude reconnect, repair or pause time from the end-to-end denominator. Initialization, invitation interaction and fixture generation need explicit inclusion/exclusion rules before any threshold is chosen. Receiver publication and the Sender's subsequent `Complete`/`CompleteAck` exchange are separately observable transitions. [Manifest totals][verified-progress], [receiver completion][receiver-attempt], [publication worker][publication], [sender completion][sender-attempt].

For Resume/cache tests, declare opening verified/cache state, distinguish recovered bytes from bytes newly made useful, and track unique work identities across Attempt/collection changes. A bare final-file-size numerator over only the last connection would credit previously transferred content again. Do not combine clocks across endpoints without a defined synchronization/error contract. Keep QUIC acknowledged bytes, source/repair payload admitted, payload received, verified logical bytes and published file bytes as separate measurements. This is measurement guidance inferred from the cited identity, progress and completion boundaries; it does not add a production telemetry API.

## Available evidence and its limits

GridCast has a `gridcast_bench` collector for receive/verify/stage spans, collection occupancy, allocations and profiles; ordinary builds compile no-op seams. Those hooks are a possible attribution aid, not existing operational fleet telemetry. [Benchmark collector][benchstats].

The retained DATAGRAM scheduling comparison is explicitly a logical simulation with chosen arrival/loss/delay inputs, not a network throughput result. Its deterministic correctness cases and native-Wire regressions are useful fixture starting points; its modeled one-millisecond Symbol emission and application-byte totals must not be promoted into a measured WAN trace. [Scheduling evidence][scheduling-evidence].

The retained durable-hydration benchmark measures warm filesystem-cache costs for 64 KiB tails and 8 MiB Blocks on one macOS/arm64 M4 Max host; it explicitly excludes network throughput guarantees. The adoption record likewise states native engagement, assembled capacity, impairment behavior and consumer performance are unmeasured there. These are source/receiver cost evidence and qualification boundaries, not a BBR baseline. [Hydration evidence][hydration], [adoption record][adoption].

The earlier pipeline qualification receipt reports 24 independently content-verified relay-only transfers using a sender and wiremux-server v0.1.2 on `mbp128` over a Thunderbolt bridge to `m4mini`, at GridCast candidate `075563ae7193735744d3bdab494088c5d7042ac9`: 256 MiB/1 GiB, cache/no-cache, pipeline/fallback, three repetitions each. Its 1 GiB no-cache pipeline times were 20.22, 20.37 and 20.48 seconds; these are historical relay pipeline timings, not current direct QUIC WAN or BBR results. The receipt names `mbp128:~/bench-p4-075563a/` raw artifacts, which were not revalidated in this investigation. The PR comment is a mutable historical receipt accessed 2026-09-23; its candidate source is immutable. [Pipeline receipt](https://github.com/GridCastIO/gridcast/pull/482#issuecomment-5305491129), [candidate source](https://github.com/GridCastIO/gridcast/tree/075563ae7193735744d3bdab494088c5d7042ac9).

## Representative workload proposal and remaining decisions

Use a real two-process GridCast transfer with the pinned graph and ordinary application scheduler as the main consumer comparison. Start with fresh content in the operator's estimated 10–50 GiB range, default bounded repair, default endpoint working budgets and a direct QUIC path confirmed in the result. Preserve file bytes and successful publication checks. These choices are a proposal grounded in operator estimates and current defaults; file count/distribution, cache state and exact interval still need acceptance.

Compare Reno and opt-in BBR under matched conditions on the tentatively prioritized macOS/arm64, Linux/amd64 and Windows/amd64 endpoints. Include a low-impairment LAN preservation case, WAN paths spanning measured or explicitly declared bandwidth/RTT/loss conditions, reverse-path/control delay and receiver-limited cases. Add targeted continuous-repair, reliable-fallback, tail/multi-file, pause/restart, Resume and relay-to-direct cutover cases where they answer specific integration questions. Measure competing flows and concurrent GridCast Transfers after the intended sharing/concurrency model is established. A relay-only run can qualify application behavior but cannot demonstrate a direct QUIC congestion-controller improvement. No numeric path matrix or pass/fail threshold is established by this proposal.

The likely controller-selection boundary is wiremux's built-in QUIC transport/session configuration before both `Dial` and `Listen`, with consumer policy propagated consistently across initial pairing, Resume and migration. Currently `Transport` exposes idle settings only, and GridCast selects the default built-in transport. `WithTransport` exists for initial Dial but is not a uniform initial/managed/migration controller API; a custom wrapper also risks failing exact built-in identity checks used by packet permission and TURN profiles. Prefer extending an explicit built-in configuration contract in the later design rather than assuming a wrapper or process-global override. This is an integration recommendation, not the API decision. [QUIC config construction][quic-adapter], [wiremux options][wire-options], [managed option domain][managed-establishment], [permission binding][packet-binding].

In the planning quic-go-fast revision, recovery constructs `NewCubicSender(..., true /* use Reno */, ...)` at connection creation and again on `MigratedPath`; public `Config` has no controller selector. The transport-design ticket must account for both construction and path-reset behavior while preserving the default. GridCast fresh-Attempt migration needs policy carried into a new connection even if same-connection QUIC migration is not used. [Recovery controller ownership][recovery], [public configuration][quic-config].

Open questions for later decisions are the quantitative bandwidth/RTT/loss/reordering and ECN matrix; endpoint CPU/storage/NIC budgets; competing-traffic policy and concurrent Transfer count; exact useful-delivery/time boundaries and cache/reconnect accounting; whether continuous mode is a primary or secondary target; which deployment topology needs qualification; and where reproducible operational traces can be obtained. These are missing inputs or acceptance/design choices, not gaps to fill with synthetic claims.
