# quic-go vs quiche vs msquic: multiplatform datapath comparison (2026-09-11)

Scope: how the three major open-source QUIC stacks — quic-go (quic-go/quic-go), quiche (cloudflare/quiche), msquic (microsoft/msquic) — implement their UDP datapaths per OS, and what that implies for quic-go-fast's macOS/Windows batching roadmap. Method: primary sources only — shallow clones in the session scratchpad (`quiche` @ `c8da372`, `msquic` @ `80a0651`, quic-go upstream master @ `fbfa1d5b` = v0.60.0-42, via the existing `keibisoft-quic-go` clone whose tree below the merge base is pure upstream), plus each project's own docs and first-party publications. Third-party benchmark repos are deliberately excluded as authority. Companion note: `docs/audits/2026-09-11-keibisoft-gso-discovery.md` (our current macOS/Windows gaps).

## 1. UDP send path

| Stack | Linux | Windows | macOS/BSD |
| --- | --- | --- | --- |
| quic-go | GSO (one sendmsg per ≤64 kB burst) | plain WriteTo, no OOB | plain sendmsg via oobConn |
| quiche (tokio-quiche/apps) | GSO (one sendmsg per burst) | plain tokio/mio send_to | plain tokio/mio send_to |
| msquic | GSO + sendmmsg combined | USO (UDP_SEND_MSG_SIZE) via WSASendMsg; WSK in kernel mode | plain sendmsg |

- quic-go: Linux GSO via a `UDP_SEGMENT` cmsg — `appendUDPSegmentSizeMsg` (`sys_conn_helper_linux.go:89`, quic-go@fbfa1d5b) with a runtime probe `isGSOEnabled` reading `getsockopt(IPPROTO_UDP, UDP_SEGMENT)` (`sys_conn_helper_linux.go:76`). No `sendmmsg` anywhere. Windows sends through `basicConn` (plain `WriteTo`, `sys_conn_windows.go:12-14` `newConn` returns `basicConn`), and darwin through `oobConn` one `sendmsg` per packet with `isGSOEnabled` hardcoded false (`sys_conn_helper_darwin.go:36`) and `appendUDPSegmentSizeMsg` stubbed to nil on non-Linux (`sys_conn_helper_nonlinux.go`).
- quiche: the core crate is sans-I/O and ships no send path at all (see §4). The in-repo I/O layers are Linux-only for offload: the mio-based apps send via nix `sendmsg` with a `UDP_SEGMENT` cmsg under `#[cfg(target_os = "linux")]` (`apps/src/sendto.rs:47-84` `send_to_gso`, GSO detection `detect_gso` at `:131`), and tokio-quiche (Cloudflare's production wrapper, in-repo) does the same with `ControlMessage::UdpGsoSegments` (`tokio-quiche/src/quic/io/gso.rs:119` `send_to`, cmsg at `:142`, `cfg(target_os = "linux")` at `:117`). On any non-Linux target both fall back to plain one-datagram `send_to` (`apps/src/sendto.rs:85`, `tokio-quiche/src/quic/io/gso.rs:178-186`). A `datagram-socket` crate in the workspace offers `sendmmsg`/`recvmmsg` helpers (`datagram-socket/src/mmsg.rs:105`/`:39`, `MAX_MMSG = 16`) but nothing in tokio-quiche or the apps calls them (grep over `tokio-quiche/src` and `apps/src` finds no users).
- msquic: the Linux epoll datapath combines both mechanisms — `UDP_SEGMENT` cmsg for GSO (`src/platform/datapath_epoll.c:2293-2298`) AND `sendmmsg` for multi-message submission (`:2386`, with a `cxplat_sendmmsg_shim` fallback at `:2339` for libcs lacking sendmmsg). Windows user mode implements USO: it resolves the `WSASendMsg`/`WSARecvMsg` extension pointers (`src/platform/datapath_winuser.c:400-497`), probes `UDP_SEND_MSG_SIZE` support at datapath init (`:503-516`), and reserves cmsg space for the per-send segment size (`:194`). Windows kernel mode uses WSK with chained `WSK_BUF_LIST` sends via `WskSendMessages` (`src/platform/datapath_winkernel.c:173-224`). The macOS/FreeBSD kqueue datapath sends one plain `sendmsg` per packet (`src/platform/datapath_kqueue.c`, verified: no sendmmsg/sendmsg_x; the only "sendmmsg" hit at `:1886` is a trace label).

## 2. UDP receive path

| Stack | Linux | Windows | macOS/BSD |
| --- | --- | --- | --- |
| quic-go | recvmmsg batch of 8, no GRO | plain ReadFrom | one packet per recvmsg (batchSize 1) |
| quiche (tokio-quiche) | GRO (UDP_GRO) | plain recv | plain recv |
| msquic | recvmmsg + GRO | URO (UDP_RECV_MAX_COALESCED_SIZE) | plain recvmsg |

- quic-go: `oobConn` reads through x/net `ipv4.PacketConn.ReadBatch` (`sys_conn_oob.go`, `batchConn` interface), which is `recvmmsg` on Linux with `batchSize = 8` (`sys_conn_helper_linux.go:24`); on darwin `batchSize = 1` (`sys_conn_helper_darwin.go:22`) because x/net ReadBatch returns a single packet there, so it degenerates to one recvmsg per packet. No `UDP_GRO` anywhere in the tree (grep empty). Windows: `basicConn` plain `ReadFrom`, no cmsg data at all.
- quiche: tokio-quiche enables `UDP_GRO` via nix `UdpGroSegment` (`tokio-quiche/src/socket/capabilities.rs:222-225`, Linux-only import at `:54`) and splits coalesced reads by the GRO segment size in the worker (`tokio-quiche/src/quic/io/worker.rs:887-888`). The `datagram-socket` `recvmmsg` helper exists but is unused by the QUIC path (see §1). Non-Linux: plain tokio `recv` — no URO, no batch.
- msquic: Linux epoll enables `UDP_GRO` at socket init (`src/platform/datapath_epoll.c:675-692`), parses the `UDP_GRO` cmsg on receive (`:1656-1657`), and reads with `recvmmsg` (`:1794`, `:1870`) — GRO and recvmmsg combined. Windows user mode implements URO: `UDP_RECV_MAX_COALESCED_SIZE` set at init (`src/platform/datapath_winuser.c:530-537`), coalesced buffers up to `MAX_URO_PAYLOAD_LENGTH` split into up to `URO_MAX_DATAGRAMS_PER_INDICATION = 64` datagrams per indication (`:54`, `:64`, `:706`, `:720`), sizes delivered via the `UDP_COALESCED_INFO` cmsg per Microsoft's `IPPROTO_UDP` docs (https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-udp-socket-options). A comment at `:580` notes a Windows Server 2022 USO/URO bug blocking TTL/DSCP receive features. macOS/BSD kqueue: plain `recvmsg`, one packet per syscall.

## 3. Advanced datapaths and event models

- msquic XDP: Windows-only. `docs/XDP.md` states flatly "MsQuic does not support Linux XDP as a datapath"; the implementation is `src/platform/datapath_raw_xdp_win.c` over microsoft/xdp-for-windows, selected through the raw datapath layer (`src/platform/datapath_xplat.c:79-119`), with Linux builds compiling `datapath_raw_dummy.c` instead (`src/platform/CMakeLists.txt`). The public performance dashboard carries a dedicated "Windows User Schannel (XDP)" configuration (https://microsoft.github.io/msquic/).
- msquic kernel mode: a full in-kernel datapath (`src/platform/datapath_winkernel.c`, WSK) shipping as the Windows kernel driver build (`platform.kernel.vcxproj`), benchmarked as "Windows Kernel Schannel" on the dashboard.
- io_uring: msquic is the only one of the three with io_uring in-tree — a complete alternative Linux datapath (`src/platform/datapath_iouring.c`, ~2,300 lines, io_uring registered buffer rings via `io_uring_register_buf_ring` at `:317`, with a TODO toward `io_uring_prep_send_zc_fixed` at `:330`), compiled INSTEAD of `datapath_epoll.c` only when the opt-in CMake flag `QUIC_LINUX_IOURING_ENABLED` defines `CXPLAT_USE_IO_URING` (`src/platform/CMakeLists.txt:28-33`, root `CMakeLists.txt:887-889`) — not the default. Neither quic-go nor quiche uses io_uring anywhere (grep over both trees: zero hits; Go's runtime netpoller is epoll-based on Linux, and tokio/mio use epoll/kqueue/IOCP readiness).
- Event models: quic-go inherits Go's runtime netpoller (epoll on Linux, kqueue on darwin/BSD, IOCP-backed on Windows) — invisible to and untunable by the library. quiche apps use mio poll and tokio-quiche uses tokio (mio underneath). msquic manages its own: epoll (`datapath_epoll.c`) or io_uring on Linux, kqueue (`datapath_kqueue.c`) on macOS/BSD, IOCP on Windows (`CxPlatEventQAssociateHandle`/`CreateIoCompletionPort`, `src/platform/datapath_winuser.c:1754-1763` and passim).

## 4. Threading and architecture

- quic-go: goroutine-per-connection — the server spawns `go conn.run()` per accepted connection (`server.go:857`) and each connection runs its own send-queue goroutine (`sendQueue.Run()` from `connection.go:587`/`:925`; `send_queue.go`), plus a transport-level `runSendQueue` goroutine (`transport.go:427`). Scheduling, work stealing, and socket readiness are delegated to the Go runtime; all connections of a Transport share one UDP socket.
- quiche: the core library is sans-I/O by design — "The application is responsible for providing I/O" (`quiche/README.md:10`); `Connection::send` fills a caller buffer (`quiche/src/lib.rs:3867`) and `send_quantum()` (`:5596`) tells the caller how large a burst (and thus a GSO super-buffer) to form. Cloudflare's production I/O layer is tokio-quiche, now open source in the same repo: a listener owns the UDP socket and "spawns a new tokio task to drive each connection" (`tokio-quiche/README.md:12`), with the per-connection I/O loop in `tokio-quiche/src/quic/io/worker.rs`. Multi-socket sharding is the application's job (the API accepts a socket array, `tokio-quiche/README.md:26-28`).
- msquic: owns its threading — "MsQuic typically creates a dedicated worker thread for each processor, which are hard-affinitized to a specific NUMA node" and "aligns its processing logic with the rest of the networking stack (including hardware RSS) to ensure that all processing stays on the same NUMA node" (`docs/Execution.md:77-80`); one `CXPLAT_WORKER` per processor (`src/platform/platform_worker.c:277-304`), library state partitioned per processor (`src/core/library.c` `PartitionCount`), with an in-tree Toeplitz hash (`src/platform/toeplitz.c`) for RSS alignment. Datapath and QUIC layers run on the same thread by default for latency, or split for throughput (`docs/Execution.md:78-79`).

## 5. Language/runtime factors (brief)

- Go (quic-go): GC pressure is managed with packet-buffer pools, but every syscall crosses the runtime's syscall machinery and the netpoller adds a wakeup hop; the library cannot pin OS threads to CPUs/NUMA nodes or choose the event mechanism. This makes syscall-count reduction (GSO/batching) proportionally more valuable than in C/Rust stacks.
- Rust (quiche): no GC, zero-cost abstractions; the sans-I/O core means datapath cost is entirely the embedder's, and Cloudflare's own layers accept tokio's readiness-model overhead in exchange for ergonomics.
- C (msquic): no runtime; direct syscalls, manual buffer/thread management, and OS-vendor-level access to platform features (WSK, XDP, IOCP, io_uring) — the reason it is the only stack with kernel-bypass and kernel-mode options.

## 6. First-party numbers

- msquic: continuous public dashboards at https://microsoft.github.io/msquic/ — secnetperf throughput (Gbps up/down), RPS, HPS, and p90 latency across five configurations (Windows Kernel Schannel, Windows User Schannel, Windows User Schannel + XDP, Windows User OpenSSL, Linux OpenSSL), per the draft-banks-quic-performance scenarios. Values are rendered live by the dashboard (not quotable statically here), but this is the only continuously published, multi-OS, first-party QUIC performance data among the three stacks.
- quiche: Cloudflare's "Accelerating UDP packet transmission for QUIC" (blog.cloudflare.com/accelerating-udp-packet-transmission-for-quic/, published by Cloudflare 2020-01-08, from the quiche team): on Linux 5.3, sequential 100 MB fetches through NGINX+quiche ran at roughly 80-90 MB/s with plain `sendmsg`; `sendmmsg` cut syscalls from ~904,539 to ~15,676, GSO to ~18,824, each yielding significant throughput gains, with sendmmsg+GSO combined best. Linux-only; no Windows/macOS numbers exist from Cloudflare.
- quic-go: no first-party benchmark numbers are published; the official performance page (https://quic-go.net/docs/quic/optimizations/) documents Linux-only GSO ("large (up to 64 kB) buffer... kernel chop[s] this buffer up"), UDP buffer sizing (~7 MB recommendation), and DPLPMTUD, explicitly without measurements.
- Credible CROSS-STACK numbers on identical hardware do not exist from any first party; each project measures only itself. Third-party matrices (e.g. interop-runner-adjacent benchmark repos) exist but are pointers only, not authority.

## 7. Implications for quic-go-fast

- Our macOS gap is real and unmatched by any reference implementation's shipped code: none of the three stacks batches UDP on macOS (quic-go batchSize 1, quiche plain send_to, msquic plain sendmsg in `datapath_kqueue.c`). The KeibiSoft `sendmsg_x`/`recvmsg_x` approach (companion note) is therefore ahead of all three upstreams on macOS — with the caveat that no major stack validates the private-syscall route, so we own the ABI risk and the benchmarking burden entirely.
- For Windows, msquic is the definitive primary-source blueprint: USO probe-and-set (`datapath_winuser.c:503-516`), URO with `UDP_COALESCED_INFO` splitting (`:530-537`, `:706`), `WSASendMsg`/`WSARecvMsg` extension resolution (`:400-497`), and the Server 2022 USO/URO feature-interaction bug note (`:580`) are all directly transcribable design decisions. But quic-go-fast must first move Windows off `basicConn` (our `sys_conn_windows.go:12-14`) onto an oobConn-style path — the same prerequisite identified in the companion note.
- Receive-side coalescing (GRO/URO) is where quic-go lags even on Linux: msquic and tokio-quiche both use `UDP_GRO`, upstream quic-go does not (recvmmsg×8 only). If we invest in receive-path work, GRO on Linux and URO on Windows likely dominate a macOS recvmsg_x port, whose in-tree benefit the KeibiSoft fork never actually realized (darwin batchSize still 1).
- msquic's epoll datapath demonstrates GSO and sendmmsg are complementary, not alternatives (`datapath_epoll.c:2386` sends multiple GSO super-buffers per sendmmsg call); quic-go's one-sendmsg-per-GSO-burst leaves Linux syscalls on the table too.
- io_uring and XDP are out of scope for a Go library on practical grounds (runtime netpoller ownership, kernel-bypass driver dependencies), and msquic itself ships io_uring only behind an off-by-default build flag — evidence that even in C the epoll+offloads path remains the production default on Linux.
