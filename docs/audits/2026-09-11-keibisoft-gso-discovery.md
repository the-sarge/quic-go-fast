# KeibiSoft/quic-go GSO/batching discovery (2026-09-11)

Research question: does https://github.com/KeibiSoft/quic-go contain GSO/segmentation-offload or sendmsg/recvmsg batching implementations for macOS and/or Windows worth adapting into the-sarge/quic-go-fast? Method: read-only clone of the fork into the session scratchpad (`scratchpad/keibisoft-quic-go`), upstream `quic-go/quic-go` added as a second remote, diff of the fork against its merge base, grep of the whole tree for Windows/macOS offload symbols, and a read-only comparison against our checkout at `fc814574` (v0.62.0-95).

## Verdict

Yes for macOS, no for Windows. The fork is upstream quic-go master plus exactly one commit that adds darwin `sendmsg_x`/`recvmsg_x` batching. The send half is well-designed and worth adapting; the receive half is wired in but effectively inert because the fork leaves darwin `batchSize = 1`, so it can never read more than one datagram per call as integrated. There is zero Windows USO/URO or `WSASendMsg` batching work anywhere in the fork.

## What the commit adds (all paths relative to the fork clone)

### Send half: sendmsg_x batching, wired and functional

- `sys_conn_sendmsg_x_darwin.go` (new, `//go:build darwin`): defines `sysSendmsgX = 481` (`SYS_sendmsg_x`), a byte-exact `msghdrX` struct matching XNU `struct msghdr_x` (the file's comment documents the 4-byte-pad ABI trap and claims offsets 0/8/16/24/32/40/44/48, size 56, verified by an external test), `sendmsgXBatch` (connected sockets, unused by the wiring), `sendmsgXBatchTo` (unconnected sockets, the one actually used — each datagram carries the destination sockaddr and a shared cmsg buffer), `sendmsgXDest`/`newSendmsgXDest` (prebuilt destination sockaddr, keyed to the SOCKET family from `getsockname`, building v4-mapped `sockaddr_in6` for IPv4 destinations on quic-go's dual-stack AF_INET6 sockets, with link-local `Scope_id` resolution), and `bePort` (network-order port). Raw `syscall.Syscall6` throughout; scratch `msghdrX`/`Iovec` slices are caller-supplied so the hot path is allocation-free.
- `send_conn_sendmsg_x_darwin.go` (new, darwin): `darwinBatch` caches per-connection dest sockaddr + scratch on the `sconn`; `(*sconn).batchSend` declines (returns `handled=false`) for <2 packets, non-UDP addrs, or an unreachable fd, builds the ECN cmsg once per batch via the same `appendIPv4ECNMsg`/`appendIPv6ECNMsg` upstream uses, and loops inside `raw.Write`: `sendmsg_x` may accept FEWER datagrams than offered, so it advances past accepted ones and resends the tail, treating no-progress/`EAGAIN` as "wait for writable". On a real error it stops and the unsent tail is dropped (QUIC loss recovery covers it, but EMSGSIZE attribution to a specific packet is lost).
- `send_conn_batch_other.go` (new, `//go:build !darwin`): `batchSend` declines, so non-darwin platforms fall through to per-packet `WritePacket` (Linux keeps its GSO inside `WritePacket`).
- `send_conn.go` (modified): adds `sconn.batch any` (darwin state, sendQueue-goroutine-only) and `(*sconn).writeBatch(bufs, gsoSize, ecn)`, which tries `batchSend` only when `gsoSize == 0` and otherwise falls back to per-packet `writePacket`.
- `send_queue.go` (modified): defines optional interface `batchWriter { writeBatch(...) }` and `maxSendBatch = 16`; `Run()` now opportunistically drains the queue (capacity 8) coalescing consecutive packets that share `(gsoSize, ecn)` into one `flush(batch)`; a differing packet flushes and starts a new batch. `flush` uses `writeBatch` when the conn implements `batchWriter`, `len(batch) > 1`, and `gsoSize == 0`; it releases every buffer, signals `available`, and preserves the `isSendMsgSizeErr` check so PMTUD keeps working.

Claimed (not reproducible from this repo) numbers in the file comments: 390 MB/s → 701 MB/s at batch 32 on a standalone spike, ~3 datagrams/syscall in-tree, wins mainly on fast bursty networks.

### Receive half: recvmsg_x batching, wired but capped at 1 by inherited batchSize

- `sys_conn_recvmsg_x_darwin.go` (new, darwin): `sysRecvmsgX = 480`; `recvmsgXConn` implements upstream's `batchConn` interface (`ReadBatch(ms []ipv4.Message, flags)`), reading up to `len(ms)` datagrams per `recvmsg_x` syscall inside `raw.Read`, decoding source sockaddrs with `parseRecvSockaddr` (unmapping v4-mapped IPv6). It is adaptive: after `recvSwitchToSingle = 32` consecutive reads of ≤1 datagram it falls back to a plain `ipv4.NewPacketConn` path (the comment measures recvmsg_x ~15% slower than plain recvmsg when reading 1 at a time), re-probing every `recvProbeEvery = 256` reads.
- `sys_conn_recvmsg_x_other.go` (new, `//go:build linux || freebsd`): `newRecvmsgXBatchConn` returns nil so those platforms keep their existing `batchConn` (Linux already batches via recvmmsg through x/net).
- `sys_conn_oob.go` (modified): in `newConn`, `if xbc := newRecvmsgXBatchConn(c); xbc != nil { bc = xbc }` swaps the batchConn on darwin.
- **Integration flaw**: the commit does not touch `sys_conn_helper_darwin.go`, which still has `const batchSize = 1` (fork clone `sys_conn_helper_darwin.go:22`, same as upstream/our repo). `oobConn` allocates `msgs := make([]ipv4.Message, batchSize)`, so `ReadBatch` is always called with a 1-element slice and `recvmsg_x` can never return more than 1 datagram in-tree — the adaptive logic will observe n≤1, flip to the fallback after 32 reads, and stay there except for periodic probes. The "~38 datagrams/syscall under flood" claim comes from the author's standalone experiment, not from this wiring. Adapting the receive half requires also raising darwin `batchSize` (Linux uses 32 through the identical `oobConn` code, so this is plausible but untested here).

### Quality caveats

- No tests, benchmarks, or CI changes are included in the commit. The comments repeatedly cite validation artifacts (`small_experiments/sendmsg_x/`, `grpc_using_quic/docs/FINDINGS.md`) that do NOT exist in the repository — they live in some external KeibiSoft workspace, so the ABI-offset verification and throughput numbers are unverifiable from this fork.
- `sendmsg_x`/`recvmsg_x` are private, undocumented XNU syscalls invoked via raw `syscall.Syscall6`: no ABI stability guarantee from Apple, and private-syscall use is a risk for Mac App Store distribution (fine for server/CLI binaries).
- `queueEntry` in the fork has only `{buf, gsoSize, ecn}`. Our `send_queue.go` (v0.62-based plus local changes) adds `metadata sendMetadata` and a handshake `feedback.publish` hook in `Run()` (our `send_queue.go:144-145`); any adaptation of the fork's `Run`/`flush` rewrite must preserve that per-entry logic.
- The fork base (v0.60.0-42) is older than our base (v0.62.0-95); the touched files (`send_conn.go`, `send_queue.go`, `sys_conn_oob.go`) exist with the same shape in our tree (`remoteAddrInfo atomic.Pointer`, `writePacket`, `batchConn`), so the port is mechanical but not a clean cherry-pick.

## What our repo currently lacks (read-only survey of /Users/josh/code/github.com/the-sarge/quic-go-fast @ fc814574)

- No `sendmsg_x`/`recvmsg_x`/`UDP_SEND_MSG_SIZE`/`WSASendMsg` references anywhere (grep over `*.go`).
- macOS: `sys_conn_helper_darwin.go:22` pins `batchSize = 1` (x/net `ReadBatch` returns a single packet on darwin) and `sys_conn_helper_darwin.go:36` hardcodes `isGSOEnabled` false; `sys_conn_helper_nonlinux.go` stubs `appendUDPSegmentSizeMsg` to nil. Net effect: one syscall per packet in both directions on macOS. The fork's five new files plus its `send_conn.go`/`send_queue.go`/`sys_conn_oob.go` hooks slot directly into this layout.
- Windows: `sys_conn_windows.go:12-14` `newConn` returns a `basicConn` — no `oobConn`, no ECN, no `batchConn`, no segmentation. One `WriteTo`/`ReadFrom` per packet. The fork offers nothing here; Windows batching would be new work on a path that currently bypasses the whole OOB machinery.

## What the OS actually supports where the fork is silent

- Windows USO (send segmentation): `UDP_SEND_MSG_SIZE` (ws2ipdef.h, `IPPROTO_UDP`) — "buffers sent by your application are broken down into multiple messages by the networking stack"; and URO (receive coalescing): `UDP_RECV_MAX_COALESCED_SIZE` — multiple received datagrams coalesced into one buffer, per-datagram size delivered via the `UDP_COALESCED_INFO` cmsg through `WSARecvMsg`. Primary source: https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-udp-socket-options (see also the driver-side USO description at https://learn.microsoft.com/en-us/windows-hardware/drivers/network/udp-segmentation-offload-uso-). Exploiting either in quic-go means first moving Windows off `basicConn` onto an oobConn-style path with `WSASendMsg`/`WSARecvMsg` — a larger lift than the darwin port.
- macOS: `recvmsg_x`/`sendmsg_x` are syscalls 480/481 in XNU (`bsd/kern/syscalls.master`, implemented in `bsd/kern/uipc_syscalls.c`): https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/syscalls.master and https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/uipc_syscalls.c. They are the only batch UDP primitives on darwin (no UDP GSO, no recvmmsg). Precedent in major stacks is limited: msquic's kqueue datapath uses plain `sendmsg`/`recvmsg`, not the `_x` variants (verified against https://raw.githubusercontent.com/microsoft/msquic/main/src/platform/datapath_kqueue.c on 2026-09-11), so the fork's approach is unusual but is the documented-in-source mechanism Apple itself ships.

## Recommendation

Adapt the send half (`sys_conn_sendmsg_x_darwin.go`, `send_conn_sendmsg_x_darwin.go`, `send_conn_batch_other.go`, and the `send_queue.go` coalescing layer reworked around our `sendMetadata`/feedback logic) — it is self-contained, allocation-free, handles the two real ABI traps (dual-stack v4-mapped sockaddr, partial-batch acceptance), and degrades safely to the existing per-packet path. Treat the receive half as a design sketch, not a drop-in: it only pays off together with a darwin `batchSize` increase the fork never made, and its adaptive single/batch switching should be re-benchmarked once `ReadBatch` actually receives a multi-message slice. Write our own ABI-offset test and loopback/burst benchmarks first, since the fork ships none. Skip the fork entirely for Windows and, if Windows throughput matters, plan USO/URO as fresh work per the Microsoft docs above.
