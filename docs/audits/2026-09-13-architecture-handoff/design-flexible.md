# Flexible-design scrutiny of the six core opportunities

Reviewed source at `fdb1af2a2c81e441ad3c855c355e136214e3fd77`. This is a design review, with no implementation or runtime reproduction. I deliberately designed extensible alternatives, then applied the deletion test and compatibility obligations. Existing dependencies are in-process details except the real socket/readers and established stream test adapters. No proposed public interface changes are needed. Recommendations: keep lifecycle and state-aware terminal disposal; keep narrow coalesced delivery; accept writer completion as small maintenance; defer received-HEADERS consolidation and field-held registry as independent projects.

## 1. HTTP/3 server admission and completion: keep, first

**Flexible alternative.** A reusable `connectionGroup` with `Admit(kind) (Lease, error)`, `Seal(mode) Completion`, and `Wait(context)` supports listener-accepted, directly supplied and raw connections, forced versus graceful closure, pluggable close callbacks, and reopenable generations. Its implementation would hide admission counting, contexts, completion publication and callback execution. Callers could write `lease := group.Admit(direct); defer lease.Release(); handle(conn, lease.Context())`.

This offers attractive locality but carries too many policies. The server is permanently closed after shutdown; reopenable generations solve no current use case. Directly supplied connections retain caller ownership, while `NewRawServerConn` is unmanaged. A general group that closes every registered connection silently changes those contracts. Callbacks also obscure which lock is held and whether waiting can deadlock.

**Recommended interface.** Keep a concrete, private server lifecycle, possibly expressed as private `Server` methods rather than a new interface type. Conceptually: `admitConnection() (admitted bool)` atomically checks the sealed state and reserves completion; `finishConnection()` releases that reservation; `sealConnections(mode)` permanently refuses admissions, cancels the appropriate existing contexts, and returns one stable completion signal. Initialization and listener registration remain coordinated with the existing server mutex. A completion signal closes exactly once after sealing and the last reservation. Every admitted call reserves before handling or launching a goroutine. Waiters never hold the mutex needed by finish. No separate public errors: rejected admissions retain `http.ErrServerClosed`.

**Caller sketch.** Both `ServeQUICConn` and the listener loop admit, install the matching deferred finish, then enter existing handling. Close and Shutdown seal while synchronized, snapshot their existing locally owned listener work, release synchronization, then perform the existing waits and error handling. An accepted connection refused after sealing needs an explicit disposition consistent with listener ownership; this cannot be left to an incidental early return.

**Evidence and regression obligations.** `http3/server.go:276–285` separates checking from counting; `310–318` does so for accepted connections. `260–265` recreates the completion channel; `268–270` closes it after an atomic decrement; `609–632` currently holds the mutex while waiting. These are source-supported hazardous interleavings, not reproduced failures. Tests need deterministic admitted-versus-sealed schedules, concurrent waiters, unused/repeated Close, cancellation, callback execution, stable signal identity, owned versus supplied listeners/connections, and unmanaged raw connections. Preserve handler completion, not merely goroutine launch accounting.

## 2. ReceiveStream terminal disposal: keep, but state-aware

**Flexible alternative.** Introduce `receiveStorage` with `Push`, `Read`, `Peek`, `SetFinalOffset`, `SetReliablePrefix`, `Cancel`, `Shutdown`, and pluggable storage/release policies. It would hide frame sorting, current-frame cursor, terminal outcomes and accounting notifications. Callers become thin wrappers around a separate receive state machine.

This moves almost the entire existing stream behind an interface nearly as complicated as its implementation. It also creates a second owner for final-size and reliable-prefix decisions. Reject that framework.

**Recommended interface.** Add a queued-entry discard operation to the existing frame sorter and centralize the stream's current-frame release operation. A private stream operation retires unread storage only after the existing stream state has established that no bytes remain deliverable. It must also consume rejected incoming STREAM-frame storage without skipping final-size validation and flow-control accounting. Callers remain the existing local cancellation, shutdown, effective remote reset and normal dequeue/EOF paths. Callbacks are taken and cleared before invocation; each transferred callback fires exactly once. Preserve the existing mutex and error precedence. A pending RESET_STREAM_AT still allows its reliable prefix to arrive and be read or peeked.

**New critical finding.** Storage presence is itself part of the current terminal-state representation. `readImpl` starts with `currentFrameIsLast && currentFrame == nil` meaning EOF (`receive_stream.go:159–162`); `peekImpl` does the same at `294–295`. If cleanup simply clears a partly read final frame during CancelRead or shutdown, the next Read/Peek reports EOF before reaching the cancellation/shutdown checks. Therefore terminal outcome must survive independently of clearing storage, or the existing EOF sentinel must be deliberately updated without changing its precedence. A generic drain function is insufficient. This is a design hazard in the proposed change, not a newly claimed existing runtime failure.

**Evidence and regression obligations.** Current EOF invokes but does not clear `currentFrameDone` (`248–254`); queue ownership transfers at `frame_sorter.go:220–231`; cancellation/shutdown do not discard storage (`415–429`, `564–569`). Local cancellation still processes final size before rejecting incoming bytes (`449–465`). Test both Read and Peek after partially consumed FIN, prior EOF, local cancellation, shutdown, effective reset, lowered duplicate reliable-size reset, queued out-of-order data, and late arriving frames. Track release callbacks and data reachability, not only pooled allocation guesses. `frameSorter.Push` may already release a cut buffer before returning an error (`162–174`), so unconditional caller PutBack on every error would double-release. The result is bounded-retention/pool-reuse hardening; no measured unbounded leak is established.

## 3. Shared coalesced delivery: keep narrowly, after correctness work

**Flexible alternative.** A `receivePipeline` accepts OS-specific `ReadBatch` adapters, metadata decoders, segmentation policies, buffer allocators, retention budgets and cleanup hooks. It exposes `Next()`, `Capabilities()` and `Close()`. Although each reader could become tiny, this combines read batching, kernel control messages, protocol delivery, storage and shutdown into a new engine. Existing ADR 0005 chooses successive concrete incoming-storage owners. Reject this design.

**Recommended interface.** A concrete private pending-delivery module with `Take() (receivedPacket, bool)`, `AcceptCoalesced(packet, segmentSize) receivedPacket`, and `DiscardPending()`. Accept consumes the already-filled coalesced-tier packet buffer, returns its first datagram and owns only undelivered siblings. It requires no pending prior receive. Missing segmentation metadata means one whole nonempty datagram; singleton receives on an enabled offload socket remain slab-backed. Take transfers responsibility and clears the popped slot. Discard consumes only undelivered siblings and is called after reader production has stopped; it never closes the socket. Ordinary/empty receives keep their existing path.

**Caller sketch.** Reader first takes a pending datagram; otherwise its existing native read and control-message parser construct a packet. The enabled, nonempty coalesced path submits that packet to this module. Existing optional `releaseReadBuffers` calls DiscardPending and additionally releases any platform-specific unread native batch slots. This gives two real adapters, Unix and Windows, without adding methods to `rawConn`.

**Evidence and regression obligations.** Unix `sys_conn_oob.go:263–284` and Windows `sys_conn_windows.go:195–214` duplicate slab wrapping, singleton fallback and sibling metadata delivery; the actual slab splitter is already shared. Unix cleanup additionally owns native batch buffers (`288–305`); Windows does not (`219–227`). The module must use the kernel-filled buffer, not allocate a second slab. Preserve sender, receive time, ECN and packet-info metadata and delivery ordering. Verify normal, singleton, multiple/tail segments, zero-length behavior, malformed segment metadata, one consumer releasing while siblings remain, cleanup after partial delivery, and Linux/Windows adapter fixtures. A neutral helper does not replace platform tests. No claimed throughput gain or lock removal is necessary to justify this modest locality improvement.

## 4. Response-writer completion: accept small maintenance

**Flexible alternative.** A `responseLifecycle.Complete(outcome)` coordinates handler panic, hijack, header inference, buffered writes, trailers, stream cancellation, closure and error policy. It would own the complete server response transaction and support configurable terminal policies. Its large outcome enum mostly restates server control flow; it crosses the stream ownership seam. Reject it.

**Recommended interface.** One private `responseWriter.finishResponse()` with no result, called once after successful non-hijacked handler completion. It hides only final Content-Length inference, Flush, then trailer flush. Panic/hijack checks and subsequent CancelRead/Close stay in `RawServerConn.HandleRequestStream`. Dependencies remain the writer's existing stream and logger; no new interface adapter is needed. Existing error behavior is log-and-continue.

**New ordering constraint.** `server_conn.go:264–265` currently attempts trailers even if Flush logged an error. `response_writer.go:273–290` logs independently. Returning the first error and short-circuiting completion would be a behavior change. The method should preserve this sequence, not invent a consolidated failure result. Partial trailer writes and `trailerWritten` behavior remain the existing implementation's responsibility.

**Regression obligations and value.** Preserve explicitly provided Content-Length, uncommitted implicit length, already-flushed headers, empty response, trailers, write failure logging, panic and hijack. The response-writer test DecodeHeaders helper is an intermediate observation operation and sometimes precedes more writes; it must not automatically become finalization. This is a small ownership improvement with one principal production caller, not a high-leverage independent architecture program. It can be a separate small patch after the server lifetime change, without being a prerequisite for other work.

## 5. Received HEADERS: defer broad consolidation; role functions are the only acceptable shape

**Flexible alternative.** `headerReceiver[T]` takes parser, encoded/decoded size policies, QPACK decoder, log strategy, error mapper and stream disposition callbacks, then returns a request/response/trailer result. This supports all current roles but its configuration interface recreates each caller's rules. It is shallow despite hiding many lines.

**Acceptable narrower design.** Concrete role methods `readRequestHeaders`, `readResponseHeaders`, and existing `decodeTrailers`, with a private shared implementation for bounded block reading/optional field collection where genuinely common. Return stage-aware failures only if callers need to distinguish encoded limit, short read, QPACK decoding and semantic validation. Keep cancellation, 431 response and connection decisions at their established callers. A role-specific method must not demand a strategy bundle or callbacks that re-export its implementation. These helpers can use real `io.Reader` test adapters and the actual decoder.

**Why defer now.** Existing `parseHeaders` and `parseTrailers` already own substantial semantic behavior. Further consolidation encounters real role differences: requests and responses emit parsed-field logging even on semantic failure; trailers emit invalid-frame logging on parse failure but no invalid event on short read (`headers.go:446–471`, `server_conn.go:130–170`, `stream.go:372–404`). Encoded request excess generates 431 and ExcessiveLoad; encoded response excess uses FrameError; read failures have different wrapping and cancellation. A common helper can preserve these, but the remaining maintenance benefit is smaller than previous code-duplication counts suggest. Keep role matrices and regression cases ready; revisit when a concrete HEADERS change would otherwise need three coordinated edits. Do not normalize logging/error behavior in a refactor.

## 6. Field-held Transport registry: defer; held-lock methods reveal the cost

**Flexible alternative.** A standalone registry has pluggable clocks, expiry policies, close-packet sinks, lifecycle notifications, connection-bound registrations, reset-token indexing, transaction callbacks and stable registry identities. Transport calls `WithAdmissionTransaction` while constructing connections; expiration notifies an outside lifecycle owner. This is extensible but exports a large synchronization protocol.

**Smallest plausible interface.** A stable field-held concrete registry preserves existing connRunner operations. It stores handler/reset-token maps, uses the existing Transport mutex, and exposes narrowly scoped held-lock operations for transport admission/close. Expiry's empty-map action must revalidate lifecycle under that same synchronization. A connection-bound adapter may package repeated callbacks, but the registry itself must remain the map key identity when migrating back to an old transport (`conn_id_generator.go:199–205`). No new mutex, allocation per packet, or asynchronous lifecycle callback is justified.

**Why this remains shallow.** `transport.go:294–326` checks close state, constructs a connection and publishes it under one lock. `510–534` seals transport, closes the server outside the lock, then snapshots/destroys handlers with deliberate unlock-before-wait. `closeServer:496–507` couples server presence, close state and map emptiness. Expiry invokes `maybeStopListening` while protected (`886–895`). Extracting maps still requires callers to understand these cross-module transactions. Exposing `AddLocked`, `EmptyLocked`, snapshots and lifecycle hooks moves data but hides little policy. Moving all those policies into the registry instead makes it another Transport. Type-cast removal is useful readability, not sufficient payoff for this many obligations.

If revisited during genuine routing work, regression requirements include admission versus closure, expiry versus new registration, stable identity over A→B→A migration, duplicate IDs, reset-token behavior, delayed closed-connection packets, single-use listener exit, and callback lock/reentrancy rules. Callback deduplication can be a small local helper now without committing to extraction.

## Recommended sequence

First establish and fix server admission/completion invariants. Next implement state-aware terminal stream disposal with explicit Read/Peek outcome preservation. Third consolidate only coalesced delivery across existing readers. A small writer-completion patch is optional maintenance after server lifecycle; it has no dependency on the receive work. Defer HEADERS consolidation and full field-held registry extraction until a concrete change demonstrates repeated maintenance cost. None requires a generic framework, new public methods, new wire behavior, or another performance campaign.
