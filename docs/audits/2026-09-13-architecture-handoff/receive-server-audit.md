## Dispositions

### F1 — R1 closure trigger is overstated — fix-now

The local-cancel wakeup is one concrete transition under ReceiveStream.mutex. Two focused Read/Peek regressions plus existing cancellation/error guards can reasonably cover it. Its multiple API callers alone do not establish the shared policy's second trigger. Mark closure not triggered and retain the small table as ordinary finite regression evidence. This reduces process obligations without reducing the wakeup contract. The parent accepted this correction.

### F2 — S1 must preserve completion of concurrent owned-listener closure — fix-now

Existing `http3/server.go:609–632,640–660` serializes owned listener.Close calls under Server.mutex. Moving calls outside that mutex is necessary when completion starts taking the same mutex, but simple independent snapshots permit overlapping closes. Real `server.go:415–434` sets closeErr and releases closeMx before onClose and handshakingCount.Wait; a second close can return while the first still performs owned listener shutdown. Consequently a concurrent HTTP Close/Shutdown can return before prior listener-close work completes even when managed connection count is zero.

Accepted bounded resolution from the parent: Server owns a private listener-close serialization mutex around owned listener Close calls only. Snapshot under Server.mutex, release it before taking listener-close serialization, release serialization before waiting for managed connection completion. Keep repeated per-call close/error behavior; do not memoize errors or invent once-only return semantics. Existing created-locally listeners are real QUIC listeners; their Transport shutdown callbacks do not require HTTP Server.mutex. No cycle was found through HTTP listener removal, which happens after Accept returns and is not awaited by native listener Close. Include a single coordinated concurrent-close case within S1's existing evidence budget.

### F3 — R2 concrete release observation needs a feasible bounded technique — fix-now

`wire.StreamFrame.PutBack` is a concrete method and `internal/wire/pool.go:21–32` offers no callback-count hook or deterministic global pool count. Do not dispatch a promise of callback-count assertions at all parser/map/stream seams while also silently requiring a new production hook or relying on sync.Pool retrieval identity/GC behavior. Use existing callback counts at sorter-owned callback seams; allow narrowly scoped temporary test-only instrumentation for concrete PutBack outcomes where necessary, then remove it. Retain ordinary parser/error tests and source ownership tracing. No global pool instrumentation framework, GC timing assertion or maintained harness is approved. The existing overflow test uses a six-byte nonpooled frame, so the ownership representative must exercise a pooled overflow allocation. The parent accepted this clarification.

### F4 — R2 trim-to-copy followed by gap-limit failure is not established in the supported first-error lifecycle — fix-now

The draft promotes copy-then-gap-error to a mandatory reachable semantic class and asks for a red regression. Source ordering alone does not establish this schedule. In `frame_sorter.go`, gap count increases only at the `startGapEqualsEndGap && adjustedStartGapEnd` insertion. Setting adjustedStartGapEnd requires starting inside a gap with no replacement; the trimming paths instead advance/remove gaps or replace existing entries. Thus a trimmed frame cannot grow a valid at-most-Max gap set past the limit. A copied frame can encounter an already excessive gap count after a previous failed Push, but production connection dispatch stops handling after the first frame error (`connection.go:1879–1886`). Current callers do not establish reusable sorter operation after that fatal error.

Use supported trim-to-copy success and ordinary gap-limit failure as separate evidence classes. Keep the central consuming Push design: it avoids relying on caller guesses and makes callback transfer explicit. Do not claim the current code demonstrates an actual production copy-then-error double return or require a synthetic post-fatal continuation test as product evidence. If desired, record defensive ownership robustness under private error paths without expanding the supported lifecycle. This is a narrower correction to the evidence argument, not a rejection of R2.
