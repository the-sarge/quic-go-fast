## 1. HTTP/3 admission and completion — do first, with a focused behavioral fix

**Question: what is the common caller actually trying to do?** Both ServeQUICConn and the listener loop need to register one managed connection before serving it, reject work once stopping begins, and unregister only after handleConn returns. They do not need a generic task registry, lease framework, or new QUIC interface.

**Preferred illustrative interface:** private methods on the existing Server: `admitConn() error`, `completeConn()`, and `beginStop(mode stopMode) (done <-chan struct{}, listenerErr error)`. Public Close and Shutdown retain their present behavior and error policy. Common usage is `if err := s.admitConn(); err != nil { return err }; defer s.completeConn(); return s.handleConn(conn)`. Listener admission follows the same operation, with completion deferred inside the launched goroutine. A plain count, sealed state and one stable completion channel are implementation details protected by the server mutex. The stop mode names immediate versus graceful cancellation; it does not add a public configuration choice.

Admission must check closure and increment in one synchronized operation. Sealing and the zero-work decision use that same synchronization. Completion closes the channel exactly once after sealing and reaching zero. Every wait occurs after releasing the mutex. NewRawServerConn remains unmanaged (`http3/server.go:457–462`). Do not replace this with a bare WaitGroup whose Add may race with Wait.

**Evidence and hidden contract:** `server.go:276–285` separates the direct-connection closed check from its count increment; `310–318` similarly separates listener cancellation checking from increment. `268–270` closes the shared channel on zero during graceful cancellation. Existing `Close:609–632` holds the mutex while waiting: adding mutex-taking completion without moving that wait would deadlock. `handleConn:594` waits for request handlers, not merely the accept loop. A safe fix should retain that accounting horizon.

**Adversarial cases:** admitted A completes after sealing; B must not slip in after the zero-work decision. Two Close callers and two Shutdown callers must all observe the same completion. Immediate Close must escalate an overlapping graceful Shutdown. An unused Server closes successfully. Shutdown retains its caller context error when it expires; listener-close errors retain the existing behavior, including Shutdown returning those errors before waiting (`650–678`). Existing Close uses first listener error, Shutdown joins errors. Do not silently improve or normalize these choices in the same patch. Preserve supplied listener/socket ownership documentation (`245–247`, `291–295`, `605–608`). The comment concerning ServeQUICConn ownership does not justify detaching managed work from the completion count.

**Testability:** ConnContext (`474–475`) runs after admission, so it can hold known-active work but cannot pause the vulnerable check-to-increment window. QUICListener.Accept can control accept return, but there is still a cancellation check after it. Existing Gosched coverage (`server_test.go:747–764`) is not deterministic characterization. Test a proposed small in-process admission seam with a scripted interleaving, and use existing real connection pairs plus ConnContext/handlers to verify public waiting and cancellation behavior. A test-only hook may characterize the original exact window if necessary; do not sell an already reproduced bug. Channel replacement in init is not independently proof of a fault: before sealing, no shutdown waiter necessarily exists. Atomic registration is the decisive obligation.

**Verdict:** substantial leverage at two callers; concentrate the state transition without creating a framework. Characterize before changing semantics. No-change leaves a credible unsafe interleaving.

## 2. ReceiveStream terminal storage — do second, but storage is not protocol state

**Preferred interface:** concrete private `releaseCurrentFrameLocked()` and `discardUnreadStorageLocked()`, plus `frameSorter.Discard()` for queued entries. Keep frame sorting, flow accounting and stream error decisions in their current owners. Illustrative usage at an effective terminal transition is `s.discardUnreadStorageLocked()`, after its existing accounting decisions. Sorter discard invokes each stored callback once, removes entries and retires pooled gap bookkeeping; the sorter is then terminal, not reusable. All stream callers hold the existing mutex. Dependencies are in-process; counting callbacks are sufficient test adapters.

**Major trap found under scrutiny:** Read checks `currentFrameIsLast && currentFrame == nil` before cancellation and shutdown (`receive_stream.go:158–168`), and Peek does the same (`294–302`). Clearing an unread final frame's storage while leaving currentFrameIsLast true invents EOF and hides the existing terminal error. Cleanup must preserve an already-reached EOF but must not create that sentinel by discarding unread bytes. Either keep that distinction explicit or separate reached-EOF state from storage. This is a prerequisite, not an optional follow-up.

Normal EOF invokes currentFrameDone but leaves the callback stored (`248–252`); make the current slot consume-and-clear its callback before invoking it. The sorter transfers ownership by deleting before Pop returns (`frame_sorter.go:220–231`). Discarding only the sorter misses an in-progress frame. Local cancel and shutdown currently leave both owners reachable (`415–429`, `564–569`). Late frames after local cancellation still need final-size/flow accounting before their storage is returned (`449–467`). Remote cancellation becomes effective only at the reliable prefix (`264–267`); duplicate reset frames may lower reliableSize before the duplicate early return (`495–505`), so they can newly trigger disposal. New frames after effective remote cancellation must not refill an abandoned storage owner.

**Do not conflate disposal with read semantics.** Current Read can copy past reliableSize in one current-frame copy (`225`, then effectiveness check `244`); a new cleanup must not quietly introduce a strict truncation rule. Preserve existing bytes/error precedence, Peek behavior, cancellation error, final-size callback timing, and Abandon accounting. Actual final EOF must continue winning over a later cancellation, as it does today.

**Verification and migration:** first prove callback conservation for current partial data, out-of-order entries, ordinary EOF followed by repeated terminal calls, local cancel before final size arrives, shutdown while Read/Peek wait, reliable-prefix reset, and a reordered smaller reliable prefix. Preserve received/consumed accounting separately from storage counts. Push's gap-limit error may occur after a small-copy callback already fired (`frame_sorter.go:162–173`); blindly PutBack on every Push error can double-return pooled storage. Either leave this separate error path unchanged initially or establish an explicit consume-on-all-paths Push contract in its own verified change. Never assume PutBack is idempotent (`internal/wire/pool.go:25–32`).

**Verdict:** worth doing for concrete retirement omissions. This is stream-frame copied storage, not retained UDP slabs, and there is no measured unbounded leak claim. No generic receive-buffer owner is needed.

## 3. Coalesced delivery — do third; the complete delivery transition earns its keep

**Preferred interface:** one private concrete `coalescedDelivery` value in each OS adapter, with `next() (receivedPacket, bool)`, `accept(p receivedPacket, segmentSize int) receivedPacket`, and `discard()`. Common read path: drain next first; perform native read and parse its metadata; on a positive coalescing-enabled read, return `delivery.accept(p, size)`; otherwise return p unchanged. The implementation adopts the already-filled coalesced-tier buffer, uses the existing slab splitter once, returns the first owned view, and holds remaining views until next/discard. Accept requires no pending delivery; it consumes p's buffer responsibility. No new socket port or general cleanup interface is needed.

**What genuinely disappears:** Unix `sys_conn_oob.go:260–284` and Windows `sys_conn_windows.go:192–215` duplicate filled-buffer adoption, missing-segment-size fallback, singleton slab policy, metadata copy and enqueue. Their next and discard loops also duplicate (`151–159`, `288–295`; Windows `159–167`, `219–227`). Partitioning is already deep in `coalesced_slab.go:61–85`; extracting only split would be pointless.

**Invariants:** positive reads on GRO/URO sockets become slabs even without segment metadata. Empty reads bypass split. Do not use getCoalescedSlab here: it allocates another backing buffer (`57–58`). Every sibling copies receivedPacket metadata (remote address reference, time, ECN, packetInfo) and changes only data/buffer; do not introduce deep-copy allocations or alter timestamp rules. Metadata immutability requirements remain those of the existing adapters. Returned packets belong to consumers; discard releases only pending views. Slab views can release concurrently on different connections; the pending queue itself stays confined to the reader and its post-read cleanup. Clear consumed slots; both implementations already do that, so no leak-fix claim. Preserve short-tail segmentation and full reference initialization before publication.

**Migration/verification:** move common transition first, preserve native syscalls/control parsing and Unix unread batch-buffer disposal. Keep the I7 private optional cleanup capability: adapters need not grow a mandatory method. Test same metadata/order for singleton/multiple/short tail; release first view before and after discard; repeated discard; each slab returned once; independent sibling release under race coverage. Native Windows and Unix adapter tests still matter. Do not claim speed or fewer allocations without measurements.

**Verdict:** higher locality for two real adapters, moderate implementation risk. No change is defensible if maintenance bandwidth is scarce; this is a coherent refactor, not a discovered runtime fault.

## 4. Response completion — worthwhile small follow-up, with unchanged error policy

**Interface:** private `(*responseWriter).finish()` called once after normal handler return. It infers Content-Length only when headers have not been written and no explicit key exists, then calls Flush and flushTrailers. Server code retains hijack and panic decisions before finish, and retains CancelRead/stream Close afterward (`server_conn.go:247–269`). No returned error and no finished-state machinery is needed for the actual one-shot caller.

**Critical error choice:** Flush already wraps FlushError and logs failure (`response_writer.go:265–289`). Existing completion attempts trailers even after flushing failed. Returning an error and stopping completion, skipping trailers, cancelling writes differently, or propagating errors would all change behavior. Keep this intentional policy until an independently justified behavior change exists.

**Tests:** empty/body/explicit-length/early-Flush/informational/trailer cases, plus failed final flush followed by attempted trailers; confirm panic and hijack never enter finish. DecodeHeaders in response-writer tests is often an intermediate flush and must not become finish automatically. Preserve existing writer tests and migrate only tests of genuine completed responses.

**Verdict:** one caller gives modest leverage, but locality is real: server_conn stops inspecting private writer bookkeeping. Cheap after correctness work, independent of coalesced delivery. No need for a response lifecycle abstraction.

## 5. Received HEADERS — defer unless a forthcoming change needs it

The common work is bounded block reading and optional QPACK-field collection, but the common caller's actual decision differs by role. Request over-limit gets 431 and ExcessiveLoad (`server_conn.go:130–170`); response encoded over-limit gets FrameError (`stream.go:372–404`); trailers preserve another reporting path (`headers.go:446–471`). Request/response emit parsed-fields qlog even when semantic parsing fails. Trailer parse failure emits invalid-frame; truncated trailer read emits neither. Preserving those choices is part of the interface.

**Best eventual design:** role-specific private functions `readRequestFieldSection`, `readResponseFieldSection`, and existing `decodeTrailers`, with small shared implementation for reading and field collection. The role-specific functions return ordinary typed results and an internal phase-preserving error (encoded limit, truncated read, semantic/QPACK failure); stream resets, 431 responses and connection decisions remain with callers. Use actual qpack.Decoder plus bytes.Reader in tests; no abstract codec port. Wrapping existing errors must preserve errors.Is/As and messages where observed.

**Why not now:** a single configurable generic reader needs role flags, logger policy and semantic parse callbacks; callers must learn nearly as much as today's code. Role wrappers are better, but introduce error-phase plumbing mainly to deduplicate several dozen lines. A callback returning an iterator that requires later “finish logging” adds ordering obligations and is especially poor depth. Existing request/response semantic parsers already share meaningful iteration/limits. Preserve no-logger allocation behavior. Table-driven matrices for each role, corruption phase and logger state are the required verification if this proceeds.

**Verdict:** actual future change pressure should unlock this. Compared with no change, immediate payoff is thin after preserving all existing policies. Drop from the near-term sequence.

## 6. Routing registry — defer structural extraction; avoid confusing type cleanup with deeper ownership

A private stable field `routing packetHandlerMap` is a credible end shape, exposing existing connRunner behavior. Common connection callers already have that interface; they should not receive extra callbacks, locks or transport-close responsibilities. Sketch: `runner := &t.routing`, pass it into connection construction, then route packets through its lookup. One stable address per Transport preserves connIDGenerator's migration-back deduplication (`conn_id_generator.go:199–210`). Never construct per-call wrapper pointers.

**Why common callers defeat the quick refactor:** doDial holds Transport.mutex across closed-state validation, construction and handler registration (`transport.go:294–326`). Closed-entry expiry holds the same mutex while deleting IDs and deciding whether a single-use transport can stop (`886–895`, `588–590`); closeServer couples handler emptiness and server state (`496–507`). Splitting a registry mutex from Transport.mutex creates new coordination protocol that this interface must hide. Preserve admission/close atomicity and revalidate any “registry empty” notification under the transport lock. A registry that merely stores the transport pointer and forwards all of this does not gain depth.

**If eventually pursued:** first move the implementation into an ordinary private owner while retaining the same synchronization domain and connRunner contract. Timer expiry and best-effort closed-packet queueing remain explicit dependencies. Defer callback reduction to a separate change; callbacks currently bind a connection. Verify migration away/back, overlapping close and admission, reset-token removal, expiry concurrent with new registrations, and single-use listener shutdown. No lock-contention or performance benefit is established.

**Verdict:** retain as a bounded later maintenance possibility. The current defined-type conversion is unattractive, but common callers already receive the useful seam. No-change presently beats creating a second synchronization system to remove it.

## Recommended order after scrutiny

1. HTTP/3 atomic admission and completion, with deterministic state-transition characterization and public integration behavior checks.
2. ReceiveStream disposal, with EOF/error-state preservation and callback conservation as prerequisites.
3. Shared coalesced delivery; independent maintenance improvement with platform-specific verification retained.
4. ResponseWriter finish; optional low-cost maintenance slice, independently schedulable after the correctness fixes.
5. Defer received-HEADERS and registry extraction until concrete change pressure creates enough leverage to justify their extra interface obligations.

The first two have credible correctness/lifetime obligations visible in source. The next two survive as narrow locality improvements. The remaining two lose much of their urgency when tested against what callers actually need. None warrants a new framework.
