# Minimal-interface scrutiny

Read-only source review at `fdb1af2a2c81e441ad3c855c355e136214e3fd77`; no implementation or tests run. ADRs 0001, 0003 and 0005 and the completed HTTP/3 exchange plan constrain this design: preserve public behavior, keep patches independently carryable, and retain successive concrete receive owners. Methods below are conceptual private interfaces, not finished production code.

## 1. HTTP/3 server admission and completion — keep, first

The existing Server should remain the module. Three private operations suffice: `admitConn() error`, `releaseConn()`, and `beginShutdown(immediate bool) shutdownSnapshot`. The snapshot contains the stable completion signal and listener/error work needed by the existing Close or Shutdown caller. These operations use the existing mutex. A successful admission increments while checking `closed`; the single deferred release decrements; shutdown seals admission and closes the completion signal exactly once when the admitted count reaches zero. Contexts and the signal initialize together once, including listener-only initialization. Zero before sealing is ordinary idle, not permanent completion.

Caller sketch: `if err := s.admitConn(); err != nil { return err }; defer s.releaseConn(); return s.handleConn(conn)`. Close obtains a snapshot, releases synchronization, then waits. Shutdown preserves its graceful-context wait and timeout escalation. No new goroutine, public methods, generic lifecycle module or interface dependency is needed.

This hides the actual problem: initialization, acceptance, count changes and completion currently obey different synchronization rules (`http3/server.go:260–270,276–286,310–318`). `init` replaces the completion channel at line 265 despite initializing contexts once. A mutex around release alone deadlocks because Close currently waits while holding that mutex (`609–632`). Prefer repairing this existing owner over a standalone lifecycle struct or WaitGroup patch: WaitGroup does not itself seal admission or fix initialization.

Adversarial cases: simultaneous direct serves; listener registration after a connection starts; acceptance paused before admission while shutdown seals; zero-active shutdown; last completion racing a new admission; repeated/concurrent Close and Shutdown; timeout escalation; initialization/control-stream failure; callbacks and handlers still running. Count includes the whole `handleConn` scope through `wg.Wait` (`509–595`). It does not make an arbitrary blocked user handler forcibly stoppable. `NewRawServerConn` remains unmanaged (`457–462`). Direct ServeQUICConn rejection must not close the caller's connection. A connection already returned by listener Accept but rejected by the new admission check needs an explicit immediate-close disposition; leaving it unserved is not a complete design. Caller-owned listeners and UDP sockets retain their documented ownership.

Recommendation: characterize the concrete admitted-before-counted schedule first, then make the narrow synchronization correction. The source-derived schedules justify priority; they are not a runtime reproduction.

## 2. ReceiveStream terminal disposal — keep, with broader ownership census

Improve ReceiveStream and its existing frameSorter, not a new buffer manager. The new private operations are `releaseCurrentFrame()` and `discardBufferedData()`; the sorter gains `Discard()` and a precise existing `Push` contract: the callback is consumed on every outcome, by queue ownership or immediate release. Release clears the callback before invocation. Discard deletes entries before callbacks and preserves stream protocol state. It is repeatable without duplicate callback invocation.

Caller sketch: local cancellation sets terminal state, disposes buffers, and wakes blocked readers; effective remote reset disposes only once readable reliable data is no longer needed; shutdown disposes buffers after recording its error. Incoming STREAM frames still perform their existing final-size/flow-control validation before a terminal stream disposes their storage. Final-size notification, completion notification, error choice and buffer disposal remain distinct obligations.

There are three important traps. First, local CancelRead sets `cancelledLocally` then returns early if `cancelledRemotely` is already set (`receive_stream.go:422–424`). Even an incomplete reliable prefix becomes unnecessary after local cancel, so disposal must precede this early return while preserving the existing remote error and STOP_SENDING suppression. Second, clearing an unread FIN-backed current frame while retaining `currentFrameIsLast` fabricates EOF: Read (`159–165`) and Peek (`294–301`) test that flag plus nil before cancellation/shutdown. Preserve only EOF that was already observable before disposal; otherwise clear that flag. Do not set `errorRead` or `completed` merely because storage was discarded. Third, frameSorter can invoke the incoming callback while copying a trimmed fragment (`162–169`) and subsequently return the gap-limit error (`172–173`). A caller-side `PutBack` on every Push error can double-return pooled storage. Make Push's consuming contract true internally instead. Its other production caller, crypto_stream.go:55, supplies nil callback.

The ownership census must also include `streamsMap.HandleStreamFrame`: lines 308–316 reject unavailable/deleted streams before ReceiveStream sees the frame, without PutBack. Either cover these two dispatch rejections as part of the same consuming-handoff rule or explicitly avoid claiming complete STREAM-frame retirement. Flow-control error rejection before Push likewise needs a clear release owner.

Separate behavioral finding: CancelRead promises immediate Read unblock (`395–399`), but the remote-reset early return does not signalRead. A reader can consume the reset wakeup while reliable bytes are missing, block again, then remain blocked after CancelRead with no more traffic. Recommend a separate characterization-first correction within terminal receiving work, rather than silently preserving a contract violation or smuggling it into a storage-only refactor.

Adversarial cases: partial current frame plus gapped queue; EOF then cancellation/shutdown; unread FIN then cancellation/shutdown; zero-data FIN; ordinary reset and reliable reset; decreasing reliable size on duplicate reset (update occurs before duplicate return at `495–505`); delayed frames after cancellation; shutdown while Read/Peek waits; duplicate, replaced, trimmed and gap-limit Push paths. Preserve existing reliable-read behavior until reset becomes effective; do not opportunistically redefine how much currently buffered data a Read returns. This addresses retained reachability and missed pool reuse, not a demonstrated unbounded leak.

## 3. Coalesced filled-buffer delivery — keep narrowly, after lifecycle work

A concrete private `coalescedDelivery` owned by each native reader can expose three operations: `start(p receivedPacket, segmentSize int) receivedPacket`, `next() (receivedPacket, bool)`, `discard()`. Start consumes an already filled coalesced-tier packet buffer, requires its pending queue empty, normalizes missing segment size, invokes the existing slab splitter once, returns the first packet and owns remaining siblings. Next transfers one sibling and clears its slot. Discard releases only undelivered siblings after the read loop stops. No operation allocates another backing receive buffer or closes a socket.

Caller sketch: reader first asks `next`; otherwise its existing native code reads bytes and metadata; for a non-empty offload-enabled read it returns `delivery.start(p, segmentSize)`. Existing optional `releaseReadBuffers` calls delivery.discard and, on Unix, additionally releases unread native batch slots. Native OS adapters remain the real seam. Existing slab lifetime, ordinary packet references, retention budgets and rawConn remain unchanged.

The shared splitter already exists (`coalesced_slab.go:61–85`); extraction earns its leverage by unifying metadata propagation, single-datagram slab treatment, transfer and cleanup across `sys_conn_oob.go:260–305` and `sys_conn_windows.go:192–227`. Both current readers already clear popped entries, so no retained-popped-packet defect is claimed. Keep front-slicing initially; a reusable index is optional and needs evidence, not a new ring abstraction.

Adversarial cases: no segmentation control message; one segment; short final segment; empty datagram bypass; non-offload path; error before start; discard after partial drain; multiple sibling consumers releasing concurrently; Unix native unread batches. Preserve the optional I7 cleanup capability at transport.go:545. The smallest credible alternative is one stateless packet-expansion helper with local pending queues; it leaves transfer/cleanup duplicated, but is preferable if the three-operation module forces reader state or platform branches into shared code.

## 4. Server response completion — keep as a small independent maintenance change

One method on responseWriter: `finishResponse()`. After a normally returning, non-hijacked handler, it infers Content-Length only if final headers are still unwritten and the key is absent, calls Flush, then flushTrailers. Preserve current error logging and the attempt to write trailers after a flush failure. No return error is needed because introducing error propagation changes existing behavior.

Caller sketch in server_conn.go: keep hijack and panic branches; call `r.finishResponse()`; keep `str.CancelRead(NoError)` and `str.Close()` afterward. This moves private field knowledge from `server_conn.go:259–265` into its actual owner without adding a type or expanding responseWriter's exported method set. It does not own request cancellation, panic recovery, hijack or stream shutdown.

Adversarial cases: untouched response; explicit Content-Length, including a present empty/nil value; HEAD; bodyless status; early header flush; declared and Trailer-prefixed trailers; Flush error; panic; hijack. Preserve the exact `headerWritten` predicate, not the similar `headerComplete` flag. Existing DecodeHeaders test helpers only flush and inspect, sometimes before subsequent writes; do not replace those with terminal completion mechanically. This is worthwhile locality at low cost, not a major new deep module.

## 5. Received HEADERS — defer the complete extraction

Request, response and trailer paths share bounded block read and QPACK collection, but their meaningful behavior differs. Requests send 431 for size violations (`server_conn.go:130–162`), responses reset with FrameError on encoded oversize (`stream.go:372–404`), and trailers omit invalid-frame logging on truncated reads while logging semantic failures (`headers.go:446–471`). Request and response log collected fields even after semantic failure. Existing parseHeaders already centralizes decoded-size accounting and validation (`headers.go:55–75`).

The truthful minimum is a pure `readHeaderBlock(r io.Reader, length uint64, max int) ([]byte,error)` with a distinguishable oversize error, leaving logging, resets and typed semantic parsing at callers. That is small but thin. A deeper three-entry-point module (`readRequestHeaders`, `readResponseHeaders`, `readTrailers`) either reproduces the existing semantic parsers or requires callbacks/configuration carrying role-specific logging and error policy. It does not presently demonstrate enough extra leverage to justify a standalone change.

Actual dependencies are io.Reader and the existing logger; keep the real decoder. Adversarial validation before any later extraction: encoded versus decoded size, truncated input, QPACK failure, partial fields, nil logger allocation behavior and all three current error/logging contracts. Reconsider only with concrete repeated changes or bugs attributable to this orchestration. Do not normalize behaviors as incidental cleanup.

## 6. Transport registry — defer extraction, reject a forced tiny interface

The current `packetHandlerMap` is a defined type with Transport's underlying representation, not a Go alias (`transport.go:800`). Replacing it with a stored registry pointer is feasible, but seven meaningful operations plus Transport lifecycle integration do not become a deep one-to-three-operation module merely by grouping them under mutation commands.

The smallest complete alternative would retain the existing connRunner interface and method behavior on a concrete registry stored once per Transport, use the same Transport synchronization for admission/publication/closure, and provide locked internal operations for Transport. Close-packet enqueue remains a callback to Transport. This preserves registry identity used by `connRunners` to deduplicate migration back to the same transport (`conn_id_generator.go:20–21,199–210`). It also preserves atomic dial admission and publication (`transport.go:294–326`) and destruction outside the mutex (`510–534`). Delayed expiry must not convert an empty observation into an unlocked stop-listening action without revalidation (`886–895`).

Caller sketch would be `runner := &t.registry`, passed wherever the old pointer conversion was used. But the implementation still shares lifecycle synchronization and callbacks; a separate lock or generic port only adds hazards. A pointer-to-Transport adapter that merely forwards everything is even shallower. Moving the methods to another file improves navigation but is not architecture improvement.

Adversarial cases: duplicate IDs, atomic two-ID insertion, reset-token removal, migration away and back, expiry during transport close, and close callbacks invoking connection destruction. No contention regression or incorrect lookup has been established. Keep the extraction as a future option if Transport work makes this coupling a repeated maintenance cost; it is lower value than the three ownership corrections and the one-method response cleanup.

## Recommended sequence

First server admission/completion characterization and correction. Second receive storage retirement, with the remote-reset/local-cancel wakeup correction explicitly scoped and tested separately. Third narrow coalesced delivery. Response completion is an independent small change and may precede coalesced delivery if a low-risk maintenance task is useful; it is not their prerequisite. Defer received HEADERS and registry extraction. No new implementation is authorized by this document.

## Follow-up: separate complete STREAM-frame consuming-handoff correction

Root's extended census checks out. `internal/wire/stream_frame.go:66–70` obtains a pooled frame then rejects excessive length without returning it; `83–84` similarly rejects offset overflow after allocation/copy. The parser owns all storage until successful return, so it must return acquired pooled storage on either rejection. This does not change parse results, validation order or the parser's public interface.

After successful parse, connection.go:1818–1823 snapshots qlog metadata but can skip handling after a previous frame's error. It must dispose the skipped frame. The snapshot at connection_logging.go:29–37 copies only stream ID, offset, length and FIN, so it does not retain the frame or payload. When dispatch proceeds, `streamsMap.HandleStreamFrame` consumes the frame on every outcome: it disposes lookup-error/deleted-stream cases, or transfers ownership to ReceiveStream. ReceiveStream likewise disposes on pre-Push rejection, or transfers the callback to the sorter; the sorter consumes it on all outcomes. This is one succession of ownership, without shared ownership, a generic parser rewrite, or another module.

Recommend an independently reviewable small slice for this complete incoming STREAM-frame handoff, distinct from disposing storage already held by an existing ReceiveStream. The scopes have different triggers: frame rejection versus terminal stream transition. They share sorter source and should therefore be integrated sequentially, but neither should promise the other's result. The handoff slice can precede terminal disposal to establish a simpler consuming contract for late arrivals; this is a practical sequencing choice, not a semantic prerequisite. The wakeup correction is a third, separate behavioral issue, for which preserving existing hang behavior is not the goal.

Finite ownership contract: one acquired pooled STREAM-frame storage obligation is either returned by parser failure; transferred to connection on parse success then returned on skip; transferred to dispatcher then returned on lookup rejection; transferred to stream then returned on validation/terminal rejection; or transferred to sorter and eventually released by duplicate/replacement/error, normal consumption or terminal discard. Nonpooled frames' PutBack remains a no-op. Error values and qlog metadata remain unchanged. Verify exactly-once callback behavior directly; do not make sync.Pool object reuse or GC timing an acceptance condition. None of this concerns the UDP datagram buffer, whose ownership was already handled separately under ADR 0005.
