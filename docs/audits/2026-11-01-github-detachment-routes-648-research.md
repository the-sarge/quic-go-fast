Research date: 2026-11-01, America/New_York. Repository baseline: `902b2a5b4012393218cb918283b9d2cefa6e608b`. Evidence for [Research what each GitHub detachment route preserves](https://github.com/the-sarge/quic-go-fast/issues/648), part of [Wayfinder map: split quic-go-fast from upstream](https://github.com/the-sarge/quic-go-fast/issues/647). This report compares routes; it authorizes no detachment, deletion, rename, transfer, or Support request. Repository APIs and the Support form were inspected read-only; no request was submitted. Existing [API compatibility](../adr/0001-upstream-compatibility.md), [module identity](../adr/0002-adopt-through-module-replacement.md), and [upstream release policy](../adr/0003-follow-stable-upstream-releases.md) remain separate accepted decisions.

## Finding

Ask Support for a case-specific preservation contract before choosing a route. The current self-service route explicitly discards repository metadata. A fresh mirror copies Git data into another repository; it is not a migration of the GitHub records surrounding that data. Historical Support-assisted detaches establish that another operation has existed, but do not establish its current availability or preservation guarantees for this repository. [GitHub detachment documentation](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/detaching-a-fork), [duplication documentation](https://docs.github.com/en/repositories/creating-and-managing-repositories/duplicating-a-repository), [recorded Support-assisted case](https://github.com/desktop/desktop/issues/9384#issuecomment-616613986)

Evidence labels below mean: **confirmed** = current official documentation or a direct observation; **inference** = a consequence of the documented mechanism, not an explicit service guarantee; **unknown** = not established by the sources inspected. Project accounts are evidence of those projects' experiences only.

## Preservation matrix

For self-service, **lost** below means explicitly enumerated in GitHub's warning; **assume lost** means covered only by its broad warning about other metadata, without an item-specific description. For Support, **unknown** means no current official item-by-item promise was found. For a fresh mirror, **not copied** is an inference from a Git-only operation: it does not mean the old repository's records are deleted if that repository is retained. GitHub distinguishes repository backups from separate wiki and metadata backups. [Detachment warning](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/detaching-a-fork), [backup scope](https://docs.github.com/en/repositories/archiving-a-github-repository/backing-up-a-repository)

| Data or behavior | Support in-place detach | Leave fork network | Fresh repository with mirror push |
| --- | --- | --- | --- |
| Git commits and authorship | Confirm scope with Support. | Commit metadata retained. | History, branches, and tags copied; fetch/push LFS objects separately. |
| Issues, numbers, comments | Unknown; require identical numbers and URLs explicitly. | Issues and comments lost; no numbering continuity. | Not copied; new repository has its own issue namespace. |
| Pull requests, reviews, comments | Unknown; distinguish PRs targeting this repository from PRs targeting upstream using its branches. | PRs and comments lost. | Not copied, including PR review records. |
| Releases and uploaded assets | Unknown, including asset IDs, download URLs, and counts. | Assume lost. | Tags copied; release records, notes, and uploaded binaries not copied. |
| Stars and watchers | Unknown today; historical positive indication below. | Lost. | Not copied. |
| Discussions and their comments | Unknown. | Assume lost. | Not copied. |
| Wiki | Unknown. | Lost. | Main-repository mirror does not copy the separate wiki repository. |
| Actions workflow files | Confirm scope with Support. | Git-tracked files expected to remain. | Copied as tracked files. |
| Actions runs, logs, artifacts, caches | Unknown. | Assume lost. | Not copied. |
| Actions secrets, variables, environments | Unknown; include repository/environment scope and access grants. | Assume lost. | Not copied; new repository requires configuration. |
| Branch protections and rulesets | Unknown; distinguish repository rules from upstream network rules. | Assume lost. | Repository settings not copied by Git. |
| Repository ID and node ID | Unknown; identical URL alone is insufficient proof. | Unknown; documentation calls the result a new repository. | New repository identity. |

The matrix's mirror column follows [GitHub's Git duplication procedure](https://docs.github.com/en/repositories/creating-and-managing-repositories/duplicating-a-repository) and [backup boundaries](https://docs.github.com/en/repositories/archiving-a-github-repository/backing-up-a-repository). Releases are GitHub objects based on tags, with separate notes and assets; retaining a tag does not establish release preservation. Secrets live at repository, environment, or organization scope, rather than in workflow files. Push rulesets can cover the entire fork network, so detachment requires checking the effective rules as well as local settings. [Release model](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), [secret scopes](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets), [fork-network rules](https://docs.github.com/en/pull-requests/reference/forks)

Issue transfer is a separate possible migration step, not part of mirroring: GitHub documents transfers between repositories of the same owner, preserving comments/assignees and redirecting the original issue URL. Matching labels/milestones can carry over. Do not assume original issue numbers or all project relationships survive, and do not extrapolate this feature to PRs. Exported metadata is also not an assured restore path: GitHub explicitly says migration archives have no supported documented restore procedure on GitHub and omit some data. [Issue transfer](https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/transferring-an-issue-to-another-repository), [archive limitations](https://docs.github.com/en/repositories/archiving-a-github-repository/backing-up-a-repository)

## URL continuity, fork status, and discovery

For an in-place Support operation, an unchanged repository URL is the desired outcome, but retention of repository, issue, release, and asset URLs must be confirmed. Self-service documentation does not specify redirect behavior. Keeping the same owner/name is not proof that old issue paths still identify the same objects.

A mirror to a different URL creates no documented redirect from the source. If the source stays available, old links still lead there. GitHub's manual detach recipe instead deletes and recreates the repository at the same location, losing associated configurations and PRs. That reuses an address; it does not migrate old metadata. Self-service disconnection is permanent. [Manual detach and permanence](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/detaching-a-fork)

Renaming is a distinct operation: GitHub redirects repository web traffic and Git operations, but reusing the old repository name breaks those redirects. Project Pages URLs and calls to Actions hosted under the old repository name have exceptions. Thus renaming the fork aside and creating a mirror at its old name does not redirect its old issue history into the mirror. **Inference:** any combined rename/detach/mirror plan needs separate URL validation. [Rename semantics](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository)

**Inference:** a successful conversion to a standalone repository should yield REST `fork=false` and GraphQL `isFork=false`; a fresh repository created without forking should do likewise. Support's exact operation remains unconfirmed. Verify these flags, repository IDs, and parent/network relationships afterward rather than using the banner alone. GitHub excludes forks from repository search by default; `fork:true` includes them and `fork:only` restricts to them. Code search uses `is:fork`. Becoming standalone removes the fork-specific discovery obstacle in principle, but establishes no ranking, indexing deadline, or external-search guarantee. [Search behavior](https://docs.github.com/en/search-github/searching-on-github/searching-in-forks)

GitHub also documents that code indexing is incomplete and searches only the default branch. Those independent limits remain after detachment. [Code-search limitations](https://docs.github.com/en/search-github/github-code-search/about-github-code-search)

## What the Support form currently asks

Direct observation on 2026-11-01: the historical [detach assistant URL](https://support.github.com/contact?tags=rr-forks&subject=Detach%20Fork&flow=detach_fork) redirected to the [current contact flow](https://help.github.com/support/contact?tags=rr-forks). The authenticated portal offered the personal `the-sarge` account with Standard support. After selecting that account and GitHub.com, choosing Repositories displayed a required subject capped at 80 characters, a required Markdown description, optional attachments capped at 50 MB, and a required topic choice. No dedicated detachment topic appeared.

Selecting the repository-feature topic, without entering or submitting content, exposed a required feature selection covering templates, releases, insights, and branches, plus a required repository URL. Other topics included invitations, migration/locked state, restoration, transfer, deletion, log requests, access, and LFS removal. This was inspection of a conditional form, not a recommendation to misclassify the request; later fields were not inspected because advancing required substantive content. [Observed form](https://help.github.com/support/contact/product-selection/repositories?tags=rr-forks)

GitHub's general instructions also describe selecting a reply address and providing a subject and explanation, full repository URLs/usernames, expected behavior, and any existing ticket reference. Those instructions and the live account/topic flow differ in presentation. Prepare the facts and let the human choose the appropriate current category; ask Support to route it if no detachment category exists. [Ticket instructions](https://docs.github.com/en/support/contacting-github-support/creating-a-support-ticket)

I want to understand the available options before authorizing any operation.

1. Do you currently offer a Support-assisted in-place detach for this specific repository and account, distinct from the destructive self-service Leave fork network operation? 2. Will that operation preserve the repository ID/node ID, owner/name, visibility, Git commits, branches, tags, default branch, and LFS objects? Which of these, if any, are recreated or changed?
3. Will every open and closed issue retain its number, ID, URL, comments, attachments, labels, milestones, assignees, sub-issue hierarchy, blocking dependencies, and project associations? Will every open, closed, and merged PR retain its number, URL, commits, reviews, review comments, checks, and attachments? 4. Will releases retain their IDs, tags, notes, draft/prerelease state, uploaded assets, download URLs, and download counts? Will stars, watcher subscriptions, discussions, wiki pages/history, and their comments retain their identities and links?
5. Will Actions run history, logs, artifacts, caches, repository/environment secrets and variables, environments and protection settings, runners, workflow permissions, webhooks, deploy keys, and installed-app access remain intact? Please identify anything requiring reconfiguration, reauthorization, or recreation.
6. Will repository branch protections and rulesets retain their IDs, required checks, enforcement, and bypass permissions? Which inherited upstream network rules cease applying, and does detachment alter any other effective permissions or security settings?
7. Will all existing repository, issue, PR, commit, release, and asset URLs continue resolving to the same records? Are any redirects needed? If we later rename the repository, what detachment-specific limitations affect those redirects, Git remotes, release downloads, Pages, or hosted Actions?
8. Will REST `fork` and GraphQL `isFork` become false and the repository become the root of its own network? What happens to existing cross-network PRs and any child forks added before execution? When should ordinary repository and code search reflect the new state, and what should we do if indexing does not update?
9. What are the current request lead time, maintenance window, unavailable operations, and expected execution time? Must we freeze writes, active Actions, releases, or new forks? What backups do you recommend, what rollback or recovery is possible, and is reattachment available for this Support operation?
10. Please list every category of data that will be lost, rewritten, disconnected, or excluded from preservation. Can you provide the proposed operation and its preservation details in writing and wait for a separate explicit authorization before making changes? If an in-place detach is unavailable, which supported alternative best preserves our issue numbering and permanent links?
