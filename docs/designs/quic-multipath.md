# QUIC multipath: sizing and design exploration

**Status:** design exploration, 2026-10-24. This note answers the sizing questions in [#646](https://github.com/the-sarge/quic-go-fast/issues/646). The owner has directed bounded native send completion, narrower initial I/O support and local queue/write timeouts treated as backpressure rather than path failure. That direction does not authorize implementation, change an existing public interface, accept the remaining D0 choices or authorize a qualification campaign. The issue stays open for a separately accepted and audited implementation handoff.

**Source baseline:** `f35df9d7b016a06174288901f3337ccc2fd7347c`. Production code is unchanged from `f1c5e2dfc0637c2c425a6ed30340adadb92098c6`; the intervening commits reconcile Q2 documentation and its journal. Protocol target: [draft-ietf-quic-multipath-21](https://datatracker.ietf.org/doc/html/draft-ietf-quic-multipath-21). Current publication status, implementation pins, and external source checks are in the [research note](../audits/2026-10-24-multipath-646-research.md). Reproducible inventory and historical counts are in the [sizing data](../audits/2026-10-24-multipath-646-sizing.json).

## Recommendation and confidence

Continue toward a conditional implementation decision. The fork has a useful packet-emission owner, explicit recovery feedback, migration tests, and native packet-I/O work to build upon. The difficult change is introducing several simultaneous path contexts into mechanisms that currently have one active context. No evidence in this investigation establishes a speed benefit, correct multipath interoperability, or production readiness.

For the full scenario including bounded native send completion, bounded path management, path-scoped local-socket migration, ordinary STREAM and DATAGRAM use, a small built-in scheduler, BBR integration, and observability, reserve **about 9,300–18,400 production lines added or deleted, 15,500–33,500 test/support lines added or deleted, and roughly 25–58 candidate review slices before native qualification**. The production forecast spans 45–65 existing principal files and 17–33 new files; secondary integration sites are not a complete touched-file forecast. These are engineering ranges, not measured diffs, calendar estimates, accepted slices, or a promise that the upper bounds will hold. Confidence is medium in the affected areas, low-to-medium in the original line forecasts, and low in the new bounded-I/O allowance and review-unit decomposition; there has been no prototype or trial port. The first consideration widened migration, submission fencing, close routing and CID admission allowances. The preceding pass added the separately identified bounded-I/O allowance below; this pass resolves nine further recommendations within that allowance.

The preferred first milestone is opt-in QUIC v1 with default Reno, two active-or-validating protocol paths, one primary with a validated backup, and application-driven migration of an existing path to another local socket without consuming a new wire path ID. Initial multipath I/O support is narrowed to qualified exact native UDP sockets with an explicit transport-wide write/deadline grant; custom wrappers, managed leases and external send callbacks are deferred. Fixed-peer, network-admitted/delegated, candidate-group and send-thread-QoS combinations remain excluded. BBR and aggregation come later; keep the scheduler private. Unregistered transports retain existing single-path I/O behavior. An opted-in transport also applies its bounded writer to non-negotiating peers and non-QUIC writes on that socket; this consequence must be explicit. A healthy supported endpoint must not leave retirement indefinitely pending behind a send. This is a local completion requirement, not a guarantee of peer cooperation or bounded restoration of redundancy.

The **Reno-first milestone is estimated at 7,770–15,130 production and 11,500–24,000 test/support line edits**. Later BBR/aggregation still adds 1,500–3,300 production and 4,000–9,500 test/support edits. Reno-first owns path-qualified recovery, credit, key updates, lifecycle, migration, bounded native sending and independent interop; it is not a codec-only release. The [first consideration response](../audits/2026-10-24-multipath-646-consideration-response.md) records the earlier findings and dispositions.

The [second consideration response](../audits/2026-10-24-multipath-646-second-consideration-response.md) is the historical disposition of eight follow-up recommendations. Its F3 recommendation to accept indefinite retirement is superseded by the owner-directed bounded-I/O direction in this revision. The [bounded-I/O design pass](../audits/2026-10-24-multipath-646-bounded-io-design-pass.md) records that historical revision and its incremental sizing. The [third consideration response](../audits/2026-10-24-multipath-646-third-consideration-response.md) addresses the nine recommendations from its review, corrects its shared-deadline trace and supersedes its permissive ordinary-peer timeout policy. The current design requires nonfatal local backpressure for both ordinary and multipath peers. Earlier notes remain historical evidence; neither the prior review nor this manual response establishes independent acceptance of this revision.

There is now a third implementation option besides writing the extension ourselves or declining it: selectively adapt an existing Go implementation. [qoke/mp-quic-go at `084c13ea`](https://github.com/qoke/mp-quic-go/tree/084c13ea3834fbe58cedb63db9208951d714f839) targets draft-21 and has a picoquic test harness. It is a source reference worth evaluating, not a drop-in patch for this fork's emission and recovery ownership. Do not apply its whole diff as the implementation plan.

## What changed since the issue was filed

- The claim that no Go implementation exists is outdated. The research note verifies a draft-21 Go reference and distinguishes inspected source from the author's reported test results.
- [Packet emission #24](https://github.com/the-sarge/quic-go-fast/issues/24) and [A20 #936](https://github.com/the-sarge/quic-go-fast/issues/936) are complete. [BBRv3 #600](https://github.com/the-sarge/quic-go-fast/issues/600) has completed all transport/controller slices and Q1; [Q2 #599](https://github.com/the-sarge/quic-go-fast/issues/599) remains outstanding and not dispatched.
- Current recovery includes default-Reno registration-prefix ordering, spurious-loss undo, and adaptive application loss thresholds. The issue's September baseline predates some of those contracts. Multipath must partition their evidence correctly, not merely instantiate several BBR senders.
- The draft is in the RFC Editor queue, with final approval pending at the inspection date. Treat -21 as the pinned target and recheck the published text before implementation; a queue position is not a guarantee of immutable text.
- Application-data packet-number spaces become per path. Initial and Handshake spaces remain connection-level; 0-RTT belongs to path zero. New extension frames are carried in 1-RTT packets. PATH_ACK is recommended for path zero, but a negotiated endpoint must still process ordinary ACK for that path. A blanket replacement of every ACK is incorrect.
- A protocol path ID is distinct from this fork's current `pathID` candidate handle and `pathGeneration` migration epoch. NAT rebinding can change the tuple of an existing path ID, and several path IDs may use the same tuple. The proposed model must represent both cases.
- Backup status signals a preference to the peer. It does not prove an idle path remains reachable, mandate zero backup traffic, or guarantee sub-RTT failover. Failure detection, NAT lifetime, and scheduling determine the outcome.
- `disable_active_migration` forbids additional paths to the peer's handshake address, while paths to other peer addresses can be permitted. Moving to a server preferred address with the same client address is path-zero migration; its CID belongs to path zero, and advertising it does not promise simultaneous use of the original and preferred addresses. The existing `AddPath` blanket rejection cannot simply be reused as the multipath rule. [Draft §2.2](https://datatracker.ietf.org/doc/html/draft-ietf-quic-multipath-21#section-2.2)

The proposed first evidence scope is QUIC v1, which the draft explicitly targets. This fork also supports QUIC v2. Preserve its version configuration and negotiation: omit the multipath transport parameter on a selected version outside the accepted support scope, and report not-negotiated capability there. Supporting v2 would require explicit version-specific key/IV/header/key-update and interop coverage; its [different derivation labels](https://www.rfc-editor.org/rfc/rfc9369.html#section-3.3.2) cannot be certified by reference to another implementation's v2 tests. This is an evidence-scope proposal, not a claim that the extension is inherently incompatible with v2.

## Proposed ownership model

Retain the connection goroutine as protocol-state owner and the private emission module as the owner of construction, registration and output handoff. Add a private path registry which owns path membership and delegates path-specific recovery and sending state. Keep shared application payload ownership in streams, the DATAGRAM queue and the retransmission owner. A second path does not create a second stream set, TLS session, or flow-control budget.

| Owner | State that belongs there |
| --- | --- |
| Connection | Handshake and Initial/Handshake spaces; shared key schedule and key phase; total AEAD limits; streams and flow control; connection lifetime; aggregate resource limits; application policy; globally unique registration identity where still useful. |
| Protocol path | Monotonic wire path ID; current tuple and a separate tuple/migration generation; local/remote CID sets; validation and anti-amplification; application PN/ACK history; loss/PTO/RTT; ECN and PMTU; controller and pacer; availability/backup preferences; retirement state. |
| Emission | Path selection before packing; immutable path-qualified packet registration; buffer ownership; per-path local pending-byte accounting plus an aggregate cap; compatible GSO batches; submission authority; completion routing back to the correct owner. |
| Application/consumer | Address discovery and admission policy, interface/socket choices, preferred use of expensive paths, identity policy, and definitions of useful payload delivery. |

Use `(path ID, application packet number)` for application transmission identity, with explicit Initial and Handshake identities. A tuple generation fences feedback about a rebinding or migration within one path; it is not a replacement for wire path ID. A late ACK for an abandoned path can retire retained evidence for that path without changing the live path's controller. Retransmitted STREAM bytes remain one logical delivery obligation, even when represented by transmissions on different paths.

The receive seam must recover path ID from the destination CID before packet-number reconstruction and AEAD opening. Today `updatableAEAD` has one `highestRcvdPN`, `largestAcked`, and first-sent/received key-phase progress. Making only the nonce path-aware would leave incorrect reconstruction and key-update behavior. Keep key phase shared; adapt [RFC 9001 §6](https://www.rfc-editor.org/rfc/rfc9001.html#section-6) to independent path spaces rather than duplicating crypto setup. [Draft §2.5](https://datatracker.ietf.org/doc/html/draft-ietf-quic-multipath-21#section-2.5) preserves the general update principles and recommends a spacing of three times the largest path PTO after confirmation before another update; it does not supply a detailed per-path confirmation state machine or an exact previous-key discard deadline.

The pre-M2 protection contract must identify the path and key generation of an acknowledged transmission independently of the ACK's arrival path. An old-phase high PN on A cannot confirm a new-phase low PN on B. Define previous/next receive-key selection, bounded old-key retention with silent or abandoned paths, and connection-wide AEAD usage counters. Per-path transition boundaries are one implementation option, not a requirement to obtain confirmation from every path. A packet whose phase bit matches the current key bypasses the baseline's old/next-key PN comparison; adversarial paper traces must distinguish that case from reordered previous-phase packets. Keep Initial/Handshake ownership and path-zero 0-RTT behavior explicit without prescribing separate concrete handler objects.

ACK history also has a carrier and a target. Today each sent packet stores one `LargestAcked` and its acknowledgment calls one `ignorePacketsBelow`. A packet sent on A that carries PATH_ACK for B must remember B's pruning boundary; acknowledging the carrier advances B's receive-history watermark, not A's. Bundled PATH_ACKs need one target association each, and ordinary ACK targets path zero. Keep this metadata path-qualified through carrier loss, retransmission or retirement; do not add a second payload-delivery owner. Existing receive history has a range cap, so this is a correctness/efficiency obligation rather than a claim that current history is unbounded.

Audit connection-wide RTT consumers separately from recovery: for example, `newFlowController` currently receives `c.rttStats`. Define the aggregate observation used for flow-control autotuning and connection-level timing, while handshake recovery and each path's loss/PTO stay with their correct owner. Choosing the lowest RTT globally without reviewing these callers would be an unexamined behavior change.

On send, the scheduler sees only paths currently eligible under validation, local/peer preference, congestion, pacing, MTU, local credit and authority. It selects a path before the packer consumes stream or DATAGRAM work. The packer receives a path-scoped context for destination CID, PN, ACK/control selection, size, and sealing. Emission then registers against that same path and enqueues immutable path metadata. Socket completion must never be attributed by consulting whichever path is preferred later.

Keep path scheduling and queue ownership behind the existing `sender` seam, with a connection-wide byte ceiling and wakeup aggregation. Path queues remain independently revocable, but every actual write on a bounded-I/O transport passes through the one endpoint writer below. A slow write on a shared socket can therefore delay other paths for its remaining operation budget; independent sockets can progress independently. The connection goroutine never waits synchronously for socket completion. Each queue releases buffers/reservations exactly once using its captured owner/generation. Pacing, credit and recovery remain per path; native capability/error state and deadline authority remain with the actual endpoint. GSO batches cannot mix destination, socket, ECN treatment or incompatible segment size. GRO splitting preserves CID-based path attribution even for equal tuples.

### Submission cutoffs and connection closure

Abandonment must stop submission, not merely new packing. Before submitting PATH_ABANDON for A on B, mark A unavailable, revoke its path-specific submission permission and establish that no submission still underway can follow the abandonment signal. Dispose unsent entries, batch tails and segmented retries through exact-once buffer/credit cleanup, and resolve their already-registered recovery obligations without making local disposal count as peer acknowledgment. The boundary must be rechecked at each actual socket submission, including retries; ordinary `sendQueue.Close` is insufficient because it drains. Do not block the connection goroutine waiting for a worker: completion of the worker fence enables signaling and later cleanup. An already completed kernel submission cannot be recalled and may arrive later. A syscall already in progress must finish or reach the declared fence before local abandonment is signaled; the draft does not guarantee a maximum time for this local operation. Remote abandonment immediately revokes future submissions when processed and resolves already-started work at the same boundary without pretending it was recalled.

Use path/tuple-generation permissions separately from connection-wide authority: retiring one path or migrating its tuple must not disable the survivor. A deterministic future case pauses A's worker with ordinary entries, a partial batch and a retry pending, abandons A via B, then resumes A and checks ordering, exact-once cleanup and reliable-data continuity. This is one semantic boundary across submission forms, not a new public authority interface.

Require bounded native send completion for the supported multipath profile. Retirement remains visibly submission-pending and charged to its path slot until completion, but the supported writer must resolve that pending I/O within the local budget below. This replaces the earlier proposal to accept indefinitely retiring paths. Completion supplies a definite accepted prefix where available, suppresses unsent tails/retries after revocation, and releases borrowed memory only after the native operation has returned. Cooperative cancellation can shorten this wait only if its acknowledgment has the same no-future-submission and no-borrowed-reference meaning. A context signal or timed-out wait by itself supplies neither guarantee.

This bounds local submission cleanup under the qualified Go/runtime/OS contract, not network failure detection, peer acknowledgment, CID credit, protocol retention, replacement validation or complete transport detachment. `WaitTransportDetachedV1` can still time out without detaching. An already submitted datagram can arrive late. Never declare callback entry to be submission, free in-use buffers, leak replacement workers to escape the path cap, or implicitly close a shared/caller-owned socket. A native implementation violating its qualified deadline contract is an endpoint fault outside the supported progress guarantee: stop admitting work there, report the fault, keep unresolved ownership quarantined within the existing caps and use surviving endpoints where possible. Even connection termination cannot safely free memory still borrowed by a non-returning operation. Do not disguise such a violation as successful bounded cleanup.

Local connection close chooses a still-usable path rather than assuming path zero survives. Stop ordinary scheduling, apply the appropriate submission cutoffs, and prepare a bounded retained close response for each selected open path context whose peer CID remains usable; a per-path cache is the proposed simple implementation. Responses retain their own DCID/PN/nonce identity and may only use a valid associated path/tuple and socket. An abandoned context is not a fallback for later cached replies. Retain CID-routing and reset-token state only within the close/resource allowance, then remove it once; received traffic cannot extend retention indefinitely. Follow [draft §2.6](https://datatracker.ietf.org/doc/html/draft-ietf-quic-multipath-21#section-2.6) for closing/draining duration based on the largest path PTO, with a bounded snapshot at transition specified in the lifecycle contract. A changed tuple alone does not make an otherwise valid ciphertext fail AEAD: CID identity determines the path. Check path-zero failure, abandonment, alternate-path close and late cached-response triggers in `closed_conn.go`, the CID generator and transport routing.

### Bounded native I/O and endpoint ownership

The first support domain is an exact, unconnected `*net.UDPConn` on a qualified OS/Go combination. Merely implementing `net.PacketConn`, exposing `SyscallConn`, embedding a UDP socket or forwarding through a managed lease is insufficient. Reject custom wrappers, registered external callbacks and managed packet-I/O registrations for multipath in this milestone, even when a callback usually forwards to a native helper. Do not unwrap them or bypass their policy. Linux is the first required interop/qualification target; macOS and Windows become supported only after the same semantic cases pass in their native venues. Other platforms remain ordinary-QUIC-only until qualified. This is a proposed support matrix, not qualification evidence.

Propose additive `Transport.ConfigureMultipathIOV1(maxWriteDuration time.Duration) error` before initialization. It binds to the exact current `Transport.Conn`, validates a finite positive budget B and grants exclusive write/deadline coordination until the observable transport-wide join below. It does not transfer socket-close ownership or change read deadlines. The caller must stop direct writes, duplicate-descriptor writers and external `SetDeadline`/`SetWriteDeadline` calls during the grant; sharing the endpoint means sharing this one Transport. Initialization may clear the prior write deadline under the grant, without promising to restore a value Go cannot query. Replacing `Conn`, late registration, duplicate ownership or unsupported socket/configuration fails locally before multipath advertisement or path attachment. Exact-pointer ownership is checked; undisclosed duplicate descriptors and direct caller interference remain explicit contract violations.

An opted-in endpoint uses this writer for all traffic, including ordinary peers, QUIC v2 and public non-QUIC writes; only wire negotiation is per connection. Unregistered transports retain their existing I/O behavior. The owner has selected **local queue and write timeouts as backpressure, not path failure**. Neither ordinary nor multipath peers may enter the existing fatal send-error path solely because a local deadline expired. Sustained lack of peer progress can still trigger ordinary handshake, idle or validation deadlines; local timeout events do not themselves advance a path-failure counter or fabricate network loss evidence.

One endpoint coordinator owns all native submissions and socket write deadlines. Go deadlines affect pending and future writes on that socket ([PacketConn contract](https://pkg.go.dev/net#PacketConn)); path workers never set them independently. The coordinator contains a control path that continues processing timers, admission, revocation and completion independently of the one potentially blocked native writer. It can be an event loop plus native worker or an equivalent mechanism, but neither native writes/deadline calls nor diagnostics/application callbacks may block the control path. First-profile server paths all use the original endpoint, so socket backpressure affects their shared capacity. Distinct client endpoints can progress independently.

#### Request lifetime, expiry and diagnostics

Each admitted request captures endpoint/connection/path/tuple generations, its payload owner, protocol-registration reference, one reserved completion record and an absolute deadline no later than admission+B. Queue wait, native calls and every GSO/batch fallback or retry share that deadline; partial progress never extends it. Completion for this bound means the native borrow has ended, local queue/buffer ownership has been resolved and the terminal result has been published. Connection-owned recovery processing can follow asynchronously in its bounded completion mailbox; it is not required for the endpoint fence to progress. Completion capacity is reserved before admission, so a stalled consumer cannot require blocking publication or unbounded result allocation.

The control path serializes transitions `queued → claimed/current → completed` and `queued → completed-unsubmitted`. The claim installs the current token before work leaves the queued owner, including deadline setup before the first syscall. Exactly one transition wins against expiry or revocation. Only a still-queued entry may be removed and reclaimed by the expirer/revoker. Claimed entries remain part of the current-request fence; their memory is not reclaimed until the writer acknowledges that no native operation can still reference it. The worker checks token permission and remaining time before every actual submission. A completion racing connection/path teardown remains generation-qualified and cannot update a replacement owner.

An independently serviced timer completes expired queued requests even while another request is in native I/O. Revocation uses that same control path and does not wait its turn behind unrelated queue service. For the A1/A2/C1 counterexample, A1 may occupy the writer until B and then C1 until 1.5B; A2, admitted at epsilon, must still complete unsubmitted at B+epsilon plus qualified control overhead. Once an entry has been claimed, expiry marks cancellation and waits for native acknowledgment rather than pretending the entry was queued. No unrelated queued work can extend a retiring generation's native fence.

Before dispatch the native writer installs only the current request's deadline, and retains its token until native return and completion handoff. Successfully clear/replace an expired deadline before another request is dispatched. Stale cancellation/completion cannot change a successor's deadline. Cancellation may shorten a matching current request's deadline only if the mechanism is qualified and token-serialized; simply waiting for its existing deadline is sufficient for this first profile. An acceleration is enabled only when all its native operations and fallbacks obey the same lifetime; otherwise choose a qualified ordinary-send path before dispatch. A goroutine timeout wrapper is not native cancellation.

Diagnostic publication inside admission, expiry, native submission, fallback, completion, fence and shutdown paths must be bounded and nonblocking. This includes the baseline GSO-failure `Debugf`/`log.Printf` dependency, logging locks, tracers and qlog sinks reached from those paths. Publish copied bounded metadata to a capped diagnostic queue or drop/coalesce it with a counter when full; never retain payload pointers. Sink execution is outside both the request/fence lifetime and subsequent endpoint/control progress. A blocked sink cannot backpressure these owners, and diagnostics are not joined as a prerequisite for returning write authority. Do not spawn one sink goroutine per event. This requirement is scoped to the bounded I/O chain, not a redesign of every repository logger.

An independently progressing overdue-token check runs even with no new producers. If a current native/deadline operation exceeds its absolute deadline plus the qualified tolerance, atomically mark that endpoint faulted, stop admission, resolve still-queued entries as unsubmitted and publish the fault nonblockingly. The current token and borrowed storage remain quarantined until actual return. A late completion reconciles acceptance and releases its ownership exactly once; it cannot reopen the endpoint or erase the recorded fault. This is a violation of the qualified local-I/O contract, distinct from a normal returned deadline/backpressure result. The guarantee assumes a responsive scheduler and qualified OS; it is not hard real time during suspension or a wedged kernel.

#### Admission and capacity notification

The endpoint count/byte cap includes queued plus current requests. Producers retain their existing bounded connection/path queues until successful admission; do not copy packets into another unbounded waiting queue. Endpoint completion records, waiter metadata and diagnostic storage have separate finite allowances. Attachment reserves one bounded readiness record per admitted connection, with at most the supported path/control subqueues; if the participant budget cannot reserve that record, reject new attachment/setup rather than let an existing participant lose its notification slot. Stateless replies and public non-QUIC writes use fixed endpoint classes with their own caps. Final values join D0's resource budget.

Arbitrate admission as well as service: eligible ready connections take bounded turns, with round-robin selection among their paths. A producer continuously refilling cannot seize newly free capacity ahead of an already-ready peer. Bound the number of privileged control turns before ordinary work receives a turn. Connection controls, including PATH_ABANDON and CONNECTION_CLOSE, use a connection-control allowance; stateless reset, Retry, version-negotiation and refusal traffic use a separate capped class and cannot consume that allowance. Avoid fixed positive reserved capacity for every possible connection; fairness is over admitted participants with pending eligible work, under finite population and continued native progress, not a universal latency promise under arbitrary demand.

Register readiness and observe the capacity-generation counter in one serialized control operation. On capacity release, advance that counter and grant/wake an eligible registered producer; recheck after registration so a release racing the registration cannot be lost. Readiness is coalesced, with no list entry per retry. Any temporary capacity grant has a bounded lease and is reclaimed on cancellation, teardown or failure to consume it, so a paused producer cannot indefinitely reserve the endpoint. When the selected request cannot yet fit available bytes, accumulate released capacity for its turn instead of repeatedly admitting smaller later arrivals ahead of it; a legal request must fit its class and endpoint caps by itself. The bounded grant lease begins once sufficient capacity is available, and existing queued/current requests continue draining while capacity accumulates. Local backpressure also schedules bounded retry/backoff rather than a tight expiry/repack loop; this scheduling state is independent of network-path health. The control allowance, grant lease and retry floor are finite D0 parameters.

#### Submission outcomes and backpressure

The endpoint result is richer than an ordinary send error. It identifies definitely accepted packets, definitely unsubmitted packets and unresolved acceptance separately. QUIC adapters consume local backpressure as a nonfatal completion event and keep their send service alive; they must not return it through the baseline `sendQueue.Run` fatal-error channel. Public `Transport.WriteTo` instead returns its documented synchronous result to the application. Neither route equates a timeout or a zero returned byte count with proof that a native attempt was unsubmitted.

| Outcome | Payload/recovery disposition | Ordinary and multipath consequences |
| --- | --- | --- |
| Queue admission refused | No ownership transfer; producer retains its entry and reservation. Register readiness for retry, or use the route's explicit best-effort drop/error rule. | Local backpressure only. No path retirement, connection destruction or congestion-loss sample. |
| Queued expiry/revocation, or native result proving zero submission | Resolve the registered packet as locally unsubmitted without PN reuse, peer acknowledgment or network-loss/RTT evidence. Return still-needed reliable information through its existing logical owner; discard an admitted unreliable DATAGRAM with bounded drop observability. Reclaim packet storage/local credit once no borrow remains. Probe accounting follows the conservative rule below. | A local deadline is nonfatal backpressure; revocation follows its already chosen lifecycle action. A non-timeout native rejection retains its distinct meaning, such as PMTU feedback for a known size rejection. |
| Known accepted prefix, including a prefix followed by timeout | Keep accepted packet flight/delivery evidence. Resolve only a proven-unsubmitted tail as local disposal; retain any uncertain tail separately. Native buffer references end only on actual return. | A following local timeout remains backpressure. Do not replay the accepted prefix or declare a path failed from local latency. |
| Uncertain native submission | Preserve possibly submitted packet registration and congestion/recovery evidence until ACK/loss/retirement resolves it. Do not relabel it unsubmitted, refund its amplification allowance, or immediately retry its encrypted bytes as fallback. Reliable information can later be retransmitted through ordinary logical recovery; DATAGRAMs are not retransmitted. | Nonfatal local timeout/backpressure when that is the error class. Ordinary peers remain alive. Duplicate or early feedback still resolves ownership exactly once. |
| Destination-specific failure other than local timeout | Resolve definite/uncertain submission separately; preserve error-specific policy, including PMTU/permission/reachability handling. | Attribute the actual destination/path error to its owner. Path eligibility or ordinary-connection termination may follow the separately accepted error policy; sharing a socket is not evidence that all destinations failed. |
| Endpoint-fatal error, or failed deadline control | Stop that endpoint's admissions/submissions, preserve unresolved ownership, and notify all affected users. | Paths on that endpoint become unavailable under endpoint-failure policy; ordinary connections there can terminate. Other endpoints may survive. Explicit Transport.Close remains a separate caller action. |

The connection owns the generation-qualified local-disposal transition for already registered packets: retire their local registration/flight obligations exactly once without treating local disposal as peer ACK or a congestion-loss event, return only reliable information still owed, and preserve consumed PNs. The endpoint releases its native buffer/queue credit independently; protocol accounting uses its reserved completion record containing immutable identity/outcome metadata and independently owned recovery references, never a pointer into a released packet buffer. Accepted or uncertain outcomes retain normal packet evidence. A PATH_RESPONSE or packet ACK can arrive before local completion; the later completion may reconcile ownership but cannot undo validation/delivery or mutate a new generation. Standard connection-level no-progress timers remain effective during sustained local backpressure; they are not reset by unsuccessful local retries.

For co-admitted A and C with deadline t0+B, a native A lasting until that deadline leaves C expired and definitely unsubmitted. C must not be dispatched merely because A returned. A later request D whose deadline remains in the future may be dispatched after deadline replacement. None of those local deadline events alone retires either server-side path or destroys an ordinary peer. Both server paths share this endpoint; the design promises finite ownership resolution and fair admission under stated conditions, not independent socket capacity for those paths or bounded restoration of redundancy.

#### Send-route adaptation and probe accounting

All routes below use the same endpoint admission/result contract. Successful admission transfers packet storage or a retained immutable reference until completion; refusal leaves ownership with the producer. Existing anti-amplification/local-send reservations are distinct from storage ownership. No connection event loop, endpoint control path or listener receive loop waits for native completion. Dedicated producers may wait only where explicitly listed; no waiting producer can hold an endpoint control lock or be needed to expire/revoke another request.

| Route / submitting owner | Admission refusal | Storage and submission permission | Completion / permitted waiting |
| --- | --- | --- | --- |
| Application, handshake and ordinary ACK/control packets / connection emission plus send worker | Retain in the existing bounded queue; fair readiness/retry. | Transfer packet buffer on admission; connection plus path/tuple generation, with Initial/Handshake ownership preserved. | Nonblocking reserved result to the owning connection; a dedicated path worker may await its result, never the connection loop. GSO/batch retries stay inside this one request lifetime. |
| Client and server validation/rebinding probes / connection emission | Keep or discard the prepared packet within the validation budget; no immediate spin or native call. | Asynchronous transfer on admission replaces the baseline synchronous borrow. Capture candidate/tuple generation, reserve amplification and publish challenge identity before any submission. | Connection-owned generation-qualified completion; no native wait. Applies to ordinary-peer rebinding on an opted-in endpoint too. |
| MTU probes / connection emission and MTU owner | Defer through existing pacing/probe scheduling; release a discarded prepared buffer once. | Transfer on admission; retain path/MTU generation and the probe's credit/reservation identity. | Asynchronous completion to that MTU/recovery owner; definitely local disposal is not PMTU network loss. |
| Live connection close / connection close owner | Preserve the bounded close obligation while allowed by its close deadline; do not grow a new queue. | Transfer or retain immutable close payload with connection/path/generation permission. | Asynchronous close result; never send through an abandoned generation. Explicit Transport.Close does not require sending it. |
| Cached close replies / closed-handler producer | Best-effort drop within the existing response policy. | Retain the cache reference or owned payload until native return; captured response/path identity and endpoint epoch remain valid. | Endpoint-owned completion releases the reference; no connection loop or native wait. Cache disposal cannot precede its outstanding references. |
| Stateless reset / transport reply producer | Best-effort drop under the stateless class cap. | Transfer its output buffer; endpoint epoch and response eligibility, without inventing a live connection/path owner. | Endpoint completion releases storage; no receive-loop wait. |
| Retry / server response producer | Best-effort drop under its capped class. | Preserve input storage only while deriving a self-contained output; transfer/retain every output backing buffer actually submitted. Endpoint/server response epoch authorizes it. | Nonblocking endpoint result and bounded diagnostic event; no listener receive-loop wait. |
| Version negotiation and refusal/INVALID_TOKEN responses / server response producer | Best-effort drop under the stateless/server-response cap. | Own the generated output, or retain input backing storage if the output aliases it; endpoint/server epoch and response policy. | Endpoint completion disposes output and any retained input once; no connection loop or receive-loop wait. |
| Public Transport.WriteTo / application caller | Return n=0 and an identifiable backpressure error without retaining the caller buffer. No hidden retry or waiter per rejected call. | On admission borrow caller bytes and a snapshot of destination metadata until the native borrow ends; endpoint epoch, with no fictitious QUIC path identity. The application must not mutate borrowed bytes meanwhile. | Synchronous adapter waits for its own result, not on an endpoint lock. Return native byte count/error, or n=0/local-deadline error for proven queued expiry. Post-close calls return n=0/closed without initialization or dispatch. |

Preserve conservative baseline probe charging: once an attempt reserves amplification bytes and commits challenge/backoff state, rejection, local expiry or zero-submission completion does not refund that allowance or decrement the committed challenge attempt. If admission is refused before those commitments, there is nothing to refund. The producer prepares and commits amplification/challenge state before offering a dispatchable request; successful admission cannot race ahead of that publication. Refusal after commit keeps the conservative charge. A queued probe's challenge remains recognizable even if a response arrives before the completion notification. Accepted and uncertain outcomes stay charged. An absolute validation deadline and challenge cap still bound retries; local send backpressure is not path-failure evidence, but it does not promise validation success. Teardown/generation change owns eventual challenge disposal. This choice avoids adding a refund protocol to the first profile.

For public WriteTo, a normal queued/native deadline result is returned within the qualified budget and finite completion overhead. If the native contract is violated and the call never returns, the synchronous adapter must also retain the caller's borrow until actual return; an overdue fault notification does not make the bytes reusable. This explicit exceptional limitation does not authorize an early return, hidden copy outside the memory budget or false successful cleanup. Native uncertainty remains visible as an error and is never represented as proof of zero submission. D0 freezes identifiable backpressure, local-deadline, uncertain-result and closed error semantics for opted-in transports; unregistered WriteTo behavior is unchanged.

#### Shutdown, grant return and entry points

Keep Transport.Close's explicit connection/listener destruction semantics and add a separate proposed `Transport.WaitMultipathIOStoppedV1(ctx context.Context) error` observation for opted-in transports. Close first seals endpoint admission and invalidates producer/response epochs, then performs existing logical shutdown. It requests asynchronous writer shutdown; its return alone does not return write/deadline authority. Post-close writes and attachments are rejected. Discard queued work through exact-once local completion, let the current native operation return under its existing budget, and join every possible producer/current submission/deadline action before publishing the stopped state. There is no obligation to send queued close replies on this abrupt-close path. Close ownership of the socket is unchanged.

WaitMultipathIOStoppedV1 observes that requested shutdown; before Close is requested it reports an identifiable not-stopping result, and on a transport without the grant it reports not-configured. Context expiry only stops waiting. Success means no old coordinator, captured producer, native call or stale cancellation can perform a future write/deadline mutation and all native borrows have ended. It returns the grant; it does not certify that past writes succeeded or restore the old deadline. The caller sets its desired write policy after success. Prior endpoint faults remain observable through their result/fault records. A native fault with unresolved references cannot produce successful join, even after connection termination. An eventual late return permits cleanup/join without reopening admission. The observer concerns transport-wide write authority; Conn.WaitTransportDetachedV1 remains the separate condition for safely closing a transport without destroying that connection's survivors.

Do not infer a grant merely from a multipath-enabled Config reaching a constructor. Validate every explicit origin/target and every server-selected configuration before advertisement or attachment. If a dynamic server configuration first enables multipath on an ungranted initialized transport, reject that selected configuration locally; never retrofit the writer. Socket-owning constructors may explicitly install the same grant on their private native transport using the D0-selected finite default B. All budgets are fixed before transport initialization. The proposed first-profile matrix is:

| Entry point | Socket owner / grant source | Enablement gate | Authority return / teardown |
| --- | --- | --- | --- |
| Explicit Transport.Dial/DialEarly/Listen/ListenEarly; OpenPathV1/MigrateV1 targets | Caller owns the native socket; exact Transport.ConfigureMultipathIOV1 grant required. | Before initialization where known, and before any selected-config advertisement or attachment. | Caller requests Transport.Close, then waits for WaitMultipathIOStoppedV1 before reusing write/deadline authority; detachment must precede Close if connection survivors are needed. |
| Package Dial/DialEarly and Listen/ListenEarly with caller PacketConn | No implicit grant; the hidden Transport is unavailable for explicit registration. | Reject requested multipath and direct the caller to an explicit Transport. Preserve disabled behavior. | No takeover occurs on rejection. Do not promise a hidden-transport detachment or socket-return observer. |
| Package DialAddr/DialAddrEarly and ListenAddr/ListenAddrEarly | Library creates/owns the native socket and explicitly installs the default-B grant on its private Transport. | Select nonzero CID defaults and qualify the endpoint before first multipath use. A late dynamic request cannot retrofit an ungranted endpoint. | Private owner joins at actual transport shutdown and disposes its owned socket; no caller-owned socket grant is returned. Existing logical Conn/Listener close semantics do not become a borrowed-socket reuse promise. |
| HTTP/3 default client Dial, using its private per-family transports | HTTP/3 owns each native socket; explicitly install the default-B grant before its first dial when the frozen HTTP/3 QUICConfig enables multipath. | Check default-dial configuration at initialization; never upgrade an already initialized private transport implicitly. | HTTP/3's private transport owner requests and joins shutdown before releasing endpoint ownership. This does not change borrowed-socket ownership through a type assertion. |
| HTTP/3 custom Dial hook | Hook/application chooses an already supported QUIC constructor, including explicit granted Transport or an Addr constructor. | The QUIC constructor enforces its grant/configuration; HTTP/3 supplies no implicit authority for the callback's socket. | The hook/application retains its transport/socket lifecycle obligations; closing the HTTP/3 connection does not certify a borrowed socket is reusable. |
| HTTP/3 Server.ListenAndServe/ListenAndServeTLS with address-created QUIC listener | Delegates to the supported ListenAddrEarly ownership path. | Grant and selected-config gates before advertisement. | Library-owned endpoint cleanup/join, with no external socket to return. Helpers exposing no multipath Config stay disabled. |
| HTTP/3 Server.Serve with caller PacketConn | No implicit grant through its hidden ListenEarly transport. | Reject requested multipath; use an explicit granted Transport and ServeListener instead. A selected enabling configuration is rejected before advertisement too. | Rejected calls do not acquire write/deadline authority. |
| HTTP/3 ServeListener / ServeQUICConn | Existing listener/connection already owns a valid negotiated transport setup. | No new grant or socket takeover. Constructor gates remain the source of multipath eligibility. | Preserve existing external listener/transport ownership; its owner performs detachment, Close and join when appropriate. |

Exact API names/errors, B/default/maximum, timer tolerance, endpoint participant/byte/control limits and platform revisions remain D0 handoff parameters. Their acceptance cannot weaken the owner-selected backpressure policy, exclusive completion ownership or explicit caller-socket grant. No public interface changes in this documentation pass.

### BBR and Reno implications

- `congestion.PacketKey` currently identifies only encryption space and PN; `packetPrefix` has three slots. Scope a controller's keys/prefixes to its path and explicitly handle the initial path's handshake spaces. Do not enlarge a global prefix array without defining how loss on one path may affect another controller.
- Delivery sampling, recovery episodes and retained indexes use a current path generation. Several live paths need independent live and retained evidence. Preserve connection registration ordinals only as an ordering aid; sample delivery, persistent congestion and undo membership must use the correct path's evidence.
- `localSendCredit` has one current generation, and ordinary reservations require old generations to drain. Treating another live path as an old generation could serialize multipath or misclassify pending transmissions. Separate per-path credit from the aggregate resource ceiling. Isolated oversized-probe reservations drain and exclude work only within their path's owner; the aggregate ceiling is a byte cap and must not impose an all-path drain. A probe on B may wait for aggregate capacity, but not for A to become empty merely to establish B's isolation.
- `deliveryPendingBytes` and application-limited inference currently describe one sender. An idle path deliberately omitted by the scheduler is not evidence that the application has no data. Make scheduler-limited sending an explicit internal fact; do not train BBR using another path's queue or application-gap observation.
- ECN counters and validation are path-specific. Cumulative receive ECT(0)/ECT(1)/CE counts, sender high-water accounting and unresolved marked-transmission evidence stay with the surviving packet-number space across same-ID tuple changes; never reset them because a socket changed. Tuple-specific capability/marking validation and generation-qualified samples are separate. Old-generation feedback must not establish new-tuple ECN capability. For deferred BBR, retain ADR 0009's rule that revalidation waits until old marked traffic is accounted for; otherwise continue without ECN. Shared key-update counters remain connection-wide. ACKs received on another path require deliberate RTT attribution; prefer same-path ACKs where usable while accepting valid cross-path ACKs and supporting abandonment/failure.
- [ADR 0013](../adr/0013-adaptive-loss-thresholds.md)'s adaptation and [ADR 0012](../adr/0012-reno-spurious-loss-undo.md)'s undo must stay path-scoped. Evidence for one path cannot relax loss thresholds or restore congestion state on another.

## Public interface alternatives

| Alternative | Benefit | Cost / limitation | Assessment |
| --- | --- | --- | --- |
| A: opt-in plus internal automatic scheduler only | Smallest external interface; easiest to evolve. | Insufficient control for backup cost policy, exact socket ownership and explicit path admission. | Too restrictive for the candidate consumers. |
| B: opt-in, explicit path handles, fixed policy choices | Hides wire/CID/recovery machinery while callers control lifecycle and preference. Existing exported `Transport`/`Path` types can support optional structural adapters. | Must define directional status, failure and migration compatibility carefully. | Preferred starting point. |
| C: public pluggable packet scheduler/controller | Maximum flexibility, including specialized distribution. | Exposes packet timing and eligibility contracts, callback reentrancy, stale snapshots and packetization coupling; risks freezing internals. | Defer until two concrete consumers establish the needed seam. |

Illustrative signatures for B follow. They describe a candidate interface, not an accepted API or compilable implementation. Primitive arguments and existing exported types follow the fork's [congestion-selection precedent](../../congestion_control.go); exact names, errors and state accessors must be settled during design acceptance.

```go
func (c *Config) ConfigureMultipathV1(enabled bool, maxPaths uint32, policy string) error
func (t *Transport) ConfigureMultipathIOV1(maxWriteDuration time.Duration) error
func (t *Transport) WaitMultipathIOStoppedV1(ctx context.Context) error
func (c *Conn) MultipathNegotiatedV1() (bool, error)
func (c *Conn) OpenPathV1(ctx context.Context, t *Transport, remote *net.UDPAddr) (*Path, error)
func (c *Conn) PathsV1() []*Path
func (c *Conn) PathChangesV1() <-chan struct{}
func (c *Conn) WaitTransportDetachedV1(ctx context.Context, t *Transport) error
func (p *Path) PathIDV1() (uint32, error)
func (p *Path) MigrateV1(ctx context.Context, t *Transport) error
func (p *Path) SetLocalUseV1(use string) error
func (p *Path) AdvertiseStatusV1(status string) error
func (p *Path) AbandonV1(code uint64) error
```

Candidate contracts:

1. Configure before Dial/Listen/GetConfigForClient returns. Disabled is the default. Initially accept `maxPaths` of 1 or 2 and the conservative primary/backup policy only; larger caps and aggregation need the later accepted profile. The cap counts active plus validating protocol paths including path zero; retained evidence and at most one validation tuple per protocol path need separate bounded allowances; a submission-pending retirement still occupies its protocol-path slot. It is not a literal `initial_max_path_id` value or lifetime path-attempt budget. Validate local cap and policy without mutation on error. Copy/Clone must preserve the selection, with no process-global side table. Before any advertisement, require nonzero local and peer CIDs: propose that opted-in socket-owning DialAddr/DialAddrEarly select a nonzero default before initializing their single-use transport. Explicit transports with an already fixed zero-length CID generator return a local configuration error; do not relabel this as peer non-negotiation. Validate selected server configurations before advertising; an advertising peer's zero-length CID is handled as the protocol error required by [draft §2.1](https://datatracker.ietf.org/doc/html/draft-ietf-quic-multipath-21#section-2.1). Caller-socket Dial/DialEarly require the explicit-Transport route under the entry-point matrix. Disabled convenience dialing retains its existing behavior.
2. A connection exposes negotiation separately from local configuration. Without peer support it carries ordinary QUIC traffic. New path operations return an identifiable not-negotiated result rather than opening another connection or silently using migration. Before negotiation completes, report handshake-incomplete rather than an ambiguous permanent absence.
3. `OpenPathV1` is client-only, uses the caller's exact transport/socket, and accepts an explicit remote endpoint for a server address already known and admitted by the application. That is necessary but not sufficient: enforce the draft's handshake-address/`disable_active_migration` restriction and distinguish preferred-address migration from new-path creation. The initial scope should require the remote endpoint to reach the server's original `Transport`, for example through its wildcard/multihomed socket. Current client `AddPath` registers CIDs on another local transport; there is no corresponding public server operation for attaching an existing connection to an unrelated server transport. Arbitrary additional server sockets need a separately accepted association/routing contract and are outside this estimate. `OpenPathV1` returns after required validation, with context cancellation and no implicit socket ownership transfer. Cancellation before commitment to path initiation releases only local reservations; once initiation consumes an ID, cancellation or validation failure follows the explicit retirement procedure below. The transport checks its own policy and CID compatibility too.
4. `PathsV1` returns a snapshot of multipath handles, including path zero and peer-created server paths; before negotiation or without support it returns an empty snapshot, distinguishable through `MultipathNegotiatedV1`. Handles remain safe after abandonment. Add bounded state/address/MTU/error snapshot access before shipping; those return types remain a design decision. `PathChangesV1` is a coalescing invalidation notification, not a lossless event log; callers resnapshot. No application callback executes on the connection goroutine. Terminal context and qlog supply complementary diagnostics.
5. Local send use and advertised peer preference are separate controls. `SetLocalUseV1("backup")` governs the local scheduler. `AdvertiseStatusV1("backup")` requests how the peer should use the path; it cannot promise peer compliance or zero incoming traffic. Validation, ACK and liveness traffic may still use a backup.
6. `AbandonV1` is idempotent locally and returns after the connection owner accepts retirement, not after peer acknowledgment, worker fencing or requeue completion. It prevents new ordinary scheduling and orders required signaling and cleanup after the submission cutoff above. Retirement/requeueing preserves existing reliable-frame ownership and per-path flight. Proposed local abandonment of the last usable path returns a distinct error unless the caller closes the connection. Remote last-path abandonment follows the protocol-specific procedure below; network loss alone uses the accepted failure/timeout policy. A pending fence remains observable as retiring and charged to its existing slot; it does not create replacement capacity.
7. Existing `AddPath`/`Probe`/`Switch`/`Close` retain their documented contracts in ordinary QUIC. On a negotiated multipath connection, legacy path methods return an explicit mode error. For locally enabled but not-yet-negotiated connections, report handshake-incomplete; for an unsupported peer, legacy migration remains available after the result is known. The proposed `MigrateV1` supplies the missing application operation in negotiated mode: on a client path, validate the existing remote endpoint through an exact, non-nil target transport, then request a same-wire-ID tuple transition. Preserve the PN sequence and key-generation identity; use CIDs associated with that path ID. It consumes no new wire path credit, so it works in negotiated-zero or exhausted-credit mode when the peer permits migration and the required CID is available. A spare CID or a successful validation is not guaranteed; report/wait for those prerequisites within `ctx` without abandoning the old tuple. Do not use this API to evade `disable_active_migration` or to select an arbitrary new remote address.
8. Transport reuse, path retirement and closing the underlying socket remain distinct. At the baseline, `Transport.close` destroys every registered connection handler, including a connection attached through `AddPath`. Preserve that explicit-close behavior: `AbandonV1` acceptance and `MigrateV1` success alone do not make a transport safe to close. The proposed connection-level detachment observation below supplies that missing condition. Attribute network I/O errors to their affected paths/sockets rather than automatically applying explicit-close semantics to every error.

For `MigrateV1`, recommend at most one locally initiated open/migrate operation at a time. Its path uses the bounded validation slot described below; independent incoming rebinding on another path may proceed. Validate before retiring the old tuple, then fence old-generation submissions and publish the new tuple to emission; do not block other paths on that fence. Keep old flight and late feedback generation-qualified while initializing appropriate RTT/controller/PMTU and tuple-specific ECN validation for the new tuple. Cumulative ECN accounting and the wire PN space persist. `MigrateV1` returns success only after cutover; cancellation before the connection owner commits cutover leaves the old tuple selected, and cancellation after that commit reports success rather than claiming rollback. A simultaneous abandonment cancels the attempt. Exact public error identities and the state-machine cutover point need acceptance before packaging M3/M4.

This proposal preserves make-before-break for a local-socket change within an existing path. It does not add a third protocol path: replacing a full slot with a different remote endpoint still requires retire-then-open and can temporarily reduce redundancy. The owner can instead choose a three-path cap or an explicit replacement operation; either changes resource and API sizing. Incoming rebinding and preferred-address path-zero migration remain protocol obligations independently of this local API. Include negotiated-zero migration, exhausted credit, two occupied slots, failed/cancelled validation, repeated replacement and old-generation feedback in the design's evidence gates.

### Target transport compatibility and detachment

Both `OpenPathV1` and `MigrateV1` must require a non-nil target with the bounded native-I/O grant and the same effective local CID length as the connection. Check the exact socket, platform qualification, exclusive endpoint owner and incompatible registrations before attachment or credit mutation. For an initialized target, use its fixed routing length; for an uninitialized target, evaluate the length its supported initialization would select, including `ConnectionIDGenerator.ConnectionIDLen()`, and preserve that choice through initialization/attachment. A four-byte connection cannot attach to an eight-byte target. Reject incompatibility with a local configuration error before CID registration, wire-ID consumption, path-credit mutation or migration cutover, preserving the existing path. Do not silently override an initialized target's decoder. A different custom generator with the same effective length is not rejected solely for being different. This is a first-profile constraint on the baseline's fixed-length routing/unpacker, not a proposal for heterogeneous-length decoding.

Propose `WaitTransportDetachedV1(ctx, t)` as an observation of this connection's attachment to an exact transport, usable in either negotiated endpoint role. It does not retire paths, migrate them or close the transport. Success means no live or validating path of this connection uses `t`, all submissions/completions through it have resolved, and its routing registrations can no longer dispatch connection destruction or send work for this connection. Retained protocol history may remain on the connection and receive late feedback through survivors. The conservative first proposal keeps old-socket routing until its needed late-packet/CID retention ends, then unregisters it and publishes detachment; no new terminal-handler design is assumed. For abandonment, use the receipt-based retention rule below. For migration, separately bound old-tuple routing retention under the migration contract without retiring the still-live wire path ID.

Detachment publication must be serialized with transport close and already-captured handler callbacks; removing a map entry alone cannot make a concurrent earlier `Close` harmless. If close wins and destroys the connection, report its terminal error rather than claiming safe detachment. `ctx` expiry stops waiting only. A nil target returns a local argument error; a non-nil transport never attached to this connection is already detached, with normal handshake/not-negotiated errors still applying. The observation covers all this connection's paths on `t`: abandoning one of two shared-socket paths cannot detach it. After success, existing attachments cannot spontaneously reappear; the caller must serialize new open/migrate operations using that transport against closing it. Other connections/listeners on the same transport remain the caller's responsibility. Accept the API and old-tuple retention bound at D0; charge detachment to its existing lifecycle/emission/public allowances; the new bounded-I/O mechanism has the separate increment above.

### Failed initiation and remote last-path abandonment

Distinguish an API request from protocol initiation. Cancellation before the connection commits an ID to an attempt and before any submission can occur releases reservations without requiring abandonment. Once committed for initiation, keep the ID consumed even if local submission is later uncertain or validation fails; conservatively close that attempt through the cutoff and `PATH_ABANDON` procedure on a survivor. The returned context error does not assert wire retirement is complete. [Draft §§3.1 and 3.4](https://datatracker.ietf.org/doc/html/draft-ietf-quic-multipath-21#section-3.4)

For received last-path abandonment, propose prompt connection closure by default. The draft also permits a client to attempt a replacement and a server to wait briefly for one; choosing those alternatives requires a bounded recovery policy at D0. Reply to abandonment when required, and retain issued-CID/PN evidence for the draft's recommended three PTOs measured from receipt of `PATH_ABANDON`. Local cancellation does not start that receipt-based timer. An unanswered local abandonment needs a bounded retention/escalation policy; expiry cannot silently erase still-required routing or authorize ID reuse. Retention capacity and safe transport detachment remain separate gates.

For handles, prefer retaining `*Path` with a private explicit mode and separate backing owners, so structural adapters can continue naming existing upstream types. A distinct multipath type avoids mixed method sets but couples optional consumers to a fork-only return type; this remains a D0 API choice. No server or path-zero handle may dereference a legacy outgoing-path manager. The proposed mode matrix is:

The additive interface still needs a compatibility review against [ADR 0001](../adr/0001-upstream-compatibility.md). The new mode errors affect explicitly opted-in behavior; they cannot be introduced into the default profile. Optional consumers should isolate fork calls using structural capability detection or a dedicated integration adapter, and continue to build with upstream. No module-path change is proposed.

A server configured to support multipath may still accept an ordinary client with a zero-length CID: omit the extension when that peer has not advertised it, preserving ordinary fallback. If the peer does advertise it with a zero-length CID, apply the mandated connection error rather than silently downgrading. This differs from a locally fixed zero-CID generator, which cannot satisfy the requested opt-in configuration.

### Scheduling, retransmission and DATAGRAM policy

Start with a private scheduler called by emission before destructive packing. Its input is a bounded immutable set of eligible path views plus work class/size requirements; its output is a path choice or the next wake deadline. It cannot mutate congestion state, admit an unauthorized address, invent credit, or retain packet/payload pointers. Keep this an internal seam so a backup policy and an aggregation policy can vary without exposing recovery internals.

Proposed initial default: prefer the primary available path; use a validated alternate when the primary is unusable under a defined failure policy. Temporary congestion-window exhaustion or local I/O backpressure does not establish path failure. The first primary/backup policy waits for endpoint capacity on a healthy primary; it does not automatically promote the backup solely because of local timeout. Independent endpoint-fatal or network-path failure can still trigger promotion. No particular failover latency is promised. Before shipping, specify the failure/recovery thresholds, backup promotion, all-paths-backup behavior and liveness budget. The design must distinguish a strict cost-sensitive standby policy from an opportunistic overflow policy.

For aggregation, compare earliest estimated delivery with simple round-robin among eligible paths. Round-robin is straightforward but can stall ordered STREAM delivery behind a slow path and is not a bandwidth weighting policy. Recommend earliest-delivery scheduling as an experiment candidate, not an established winner; acceptance requires mixed-delay and shared-bottleneck results. No default controller change is implied.

Retransmit lost reliable information on any eligible path by default, with same-path preference while it remains healthy. Preserve mandatory same-path controls such as PATH_CHALLENGE/PATH_RESPONSE. The retransmission owner tracks logical STREAM ranges/control obligations; each newly transmitted packet uses the destination path's PN, nonce, flight and congestion allowance. Do not retransmit an encrypted packet unchanged. An ACK for an original after retransmission must not double-retire logical work or another path's congestion flight. Application DATAGRAM messages remain unreliable and are not automatically retransmitted or duplicated.

GridCast's distinct rateless symbols fit nonduplicating DATAGRAM distribution, but ordinary packet scheduling cannot promise exact application-symbol placement or equal unique payload per path. If the consumer needs explicit per-message steering, size a later `SendDatagramOnPath`-style seam with queue/MTU/admission semantics. Do not smuggle application payload classification into a packet callback. That optional public steering feature is outside the core estimate; a small internal datagram eligibility change is included.

Each path has its own PMTU. A shared DATAGRAM queue must either admit only sizes usable by every path selected for that message or retain a set of eligible paths and define what happens when that set disappears. Prefer the conservative common eligible-path size for the first generic policy, with an explicit error/limit on admission. Existing send admission never guaranteed delivery, but a new path must not silently promise a lifetime-fixed maximum. Preserve the existing first-path-only meaning of `PathMTUSettledV1`; introduce separate per-path observations rather than rewriting that contract. Reconcile the consumer's maximum-payload contract in wiremux #1738 before offering explicit steering.

Admission alone is insufficient when eligibility changes while a message is queued. The packer's existing Pop-on-no-fit branch assumes one path and distinguishes ACK pressure through `pl.ack`; PATH_ACK representation must preserve that distinction. Do not discard a message because the selected path or current packet lacks room if another eligible path/current fresh packet can carry it. Defer to a fitting path or a fresh packet without destructively consuming the message. If no eligible path can carry it, apply a declared bounded expiry/drop policy and observability rather than retaining it indefinitely. Add focused smaller-MTU and PATH_ACK-space cases; ordinary unreliable DATAGRAM semantics do not justify knowingly dropping usable queued work at the wrong packing boundary.

### Restricted transports and consumer policy

Recommend that `ConfigureFixedPeerV1` and negotiated multipath be mutually exclusive in the first supported configuration, with a local configuration/initialization error before advertising the extension. It promises one immutable remote endpoint and current local socket; extending it into a mutable peer set would contradict [ADR 0006](../adr/0006-explicit-external-packet-io.md) and the existing method contract. Do not silently broaden its permitted addresses, even if the peer is authenticated.

Apply the same first-scope exclusion to `ConfigureNetworkAdmissionV1`, including delegated admission, and to candidate groups. This is an independent restriction: `checkPathPolicy` rejects network-restricted attachment, and candidate-group membership requires network admission. Reject an incompatible origin before advertisement and an incompatible target before initialization/attachment; cover server-selected configurations and peer-created paths as well as local opening/migration. Delegating callbacks does not remove the existing restricted profile. This retains accepted restrictions rather than interpreting successful path validation as authorization.

Supporting these profiles later requires an accepted matrix for same-group, different-group and ungrouped attachments, exact local/remote admission, `disable_active_migration`, authority binding/revocation and multi-transport close/drain. The full forecast here does not include that redesign. A wiremux consumer using the restricted profile therefore cannot be the first adopter without separate policy work; a general application or transport fixture on qualified native transports is the proposed first evidence consumer. The server-original-transport limit alone does not forbid other addresses on a wildcard socket.

wiremux currently retains its selected-peer wrapper. It must separately decide whether that wrapper can authorize a set of candidate pairs and preserve exact socket ownership. QUIC path validation proves reachability under transport keys; it does not supply wiremux's address-admission or identity policy. This note does not amend wiremux ADRs or select one of #1738's architecture shapes. Address Discovery #644 and ACK Frequency #645 are independent extensions, not protocol prerequisites for multipath; their path attribution/ACK policies should be reviewed at shared seams if implemented first.

### Resource and anti-amplification proposal

The baseline incoming migration manager already caps candidate slots at three, tracks challenge count and validation deadlines, and reserves actual probe bytes before I/O. Preserve those properties but do not confuse that candidate cap with a negotiated multipath limit. Existing outgoing path handles and exponentially bounded probe retries do not constitute a connection-wide multipath resource policy.

Propose an initial local cap of two active or validating protocol paths including path zero, with submission-pending retirement still charged to that cap. Allow at most one locally initiated open/migrate operation and at most one active validation candidate per protocol path, two connection-wide. An open consumes a protocol-path slot and validates its initial tuple there; an established path may instead validate one extra tuple for migration/rebinding without a new PN space/controller history. This deliberately replaces the former single connection-wide candidate allowance. Use separate bounded allowances for fenced retained paths and pending requests. Final byte/count limits and the increased lightweight candidate allowance need measurement and D0 acceptance; no supported mode is ready without that gate. Never allocate arrays proportional to a peer maximum or sparse ID. IDs are monotonic and unreusable; increasing MAX_PATH_ID restores credit without creating unbounded simultaneous state.

Key validation candidates by wire path ID, tuple and generation; equal tuples on different IDs remain distinct. A backup open on path 1 and peer rebinding on established path 0 can each use its path's candidate slot, as can simultaneous rebinding on both established paths. Local and incoming attempts for the same path serialize: retain the admitted candidate until its absolute deadline, completion or cancellation, rather than replacing it on each new tuple. Additional tuples get no extra candidate or borrowed amplification budget; resource-limited validation may be deferred and the peer must retry. Reject/defer a competing local operation within its `ctx`. When incoming work is already admitted, do not displace it for a new local operation. Bound challenge retries and pending control state, never refresh the absolute validation deadline merely because more traffic arrives, and retain a slot while cancellation awaits an outstanding submission fence. Each unvalidated tuple uses only its own received-byte allowance. This supplies bounded contention behavior without promising service for arbitrarily many simultaneous tuple changes.

For the proposed cap of two, initially advertise `initial_max_path_id=1` (cap one uses zero), and proactively issue a small CID window for the lowest eligible unused path ID allowed by both endpoints. Propose two CIDs per used/openable path, subject to the peer's per-path active-CID limit and aggregate allowance, so one can serve a subsequent tuple change. Do not issue for a path ID beyond either current limit. Maintain at most one unused path-ID issuance window; raise local MAX_PATH_ID one step only when consumed/abandoned membership and retention budgets permit replenishment. Because grants cannot be withdrawn, retain bounded metadata for already issued IDs and handle reordering without assuming sequential arrival. Skipped IDs and consumed failures do not justify proportional allocation. Resolve PATHS_BLOCKED/PATH_CIDS_BLOCKED by credit/issuance or a controlled decline; replenishment need not wait for every old ACK if separate retention capacity is available. This is a proposed policy derived from [draft §§3.1–3.2](https://datatracker.ietf.org/doc/html/draft-ietf-quic-multipath-21#section-3.2), not a claim that the draft mandates eager allocation of all allowed IDs.

For full-slot replacement, propose **no new unused-ID pre-grant while both protocol slots are charged**. Existing grants cannot be withdrawn. A fenced retiring path may leave the live-cap accounting only after its retained state has reserved capacity; its unresolved submissions cannot be relabeled as lightweight retained history. At that transition, replenish by one ID without waiting for all old packet ACKs, subject to both endpoints' independent limits and CID availability. If retention is full, keep admission blocked rather than increase memory or forget issued IDs.

| Replacement step (client C, server S) | Grants and usable CID sets | Membership / consequence |
| --- | --- | --- |
| Paths 0 and 1 established | C and S each advertise maximum 1; each has supplied CIDs for 0 and 1. No ID-2 grant or CID window is added while both slots are charged. | Two live slots on each endpoint. |
| C requests retirement of 1; its submission fence is pending | Grants stay 1; there is no new ID-2 window. | C keeps slot 1 charged and cannot open a replacement. Path 0 can carry traffic. Qualified native sends resolve within the local completion budget; peer credit, retention and validation remain independent gates. |
| C completes the fence, sends abandonment on 0 and reserves retained-state capacity | C can advertise maximum 2. It withholds ID-2 CIDs until S's maximum also allows 2. | C has live path 0 plus retained path 1; S may still have live path 1. No assumption of simultaneous state transitions. |
| S processes abandonment and completes its own cutoff/retention admission | S can send reciprocal abandonment and advertise maximum 2. Each endpoint issues its bounded ID-2 CID set once both maxima permit it; missing control frames/CIDs still gate opening. | Each can now hold path 0, retained path 1 and a validating path 2 within separate allowances. Receipt of abandonment starts each endpoint's retention interval. |
| Both endpoints have the usable ID-2 CIDs needed for initiation | C initiates 2; validation uses its own path slot and tuple amplification accounting. | Successful validation restores two usable paths. Late ACKs for 1 affect retained evidence only. |
| Asymmetric credit or full retention | If S stays at maximum 1, or has not supplied an ID-2 CID, C waits/reports blocked within the open context and may use the protocol's blocked signals. | No ID reuse, forced peer grant or silent third slot. Path 0 alone may continue. |

This is a proposed example for D0, not a fixed packet sequence or latency promise: control frames can be bundled, lost or reordered, and receipt of one does not imply receipt of another. Measure time to restore redundancy separately from time to resume useful traffic; it includes fence progress, credit/CID exchange and replacement validation. A future pre-grant policy would need a separate admission/decline tradeoff.

Bind each locally issued CID to a wire path ID and bounded routing/reset metadata before publishing it. On ingress, use that binding for PN reconstruction and authentication without allocating a full controller/history from an unauthenticated tuple. Only authenticated input can request validating membership; apply the local live/validation/resource limits, recognize previously validated tuples where allowed, and allocate heavier state at the appropriate validated stage. The server must accept legal authenticated packets for an unused issued ID even if they contain no PATH_CHALLENGE; if it declines the path, send the required abandonment on a usable path and retain only bounded terminal metadata. Include CID issuance, reset tokens, retained close responses and tombstones in the idle-server-per-connection memory measurement, not only BBR stores. Outstanding grant, live membership, retiring evidence and tuple candidate are four different quantities.

Track pre-validation sent/received bytes on the actual path and apply the draft/RFC anti-amplification rules independently there; traffic on an established path does not buy amplification credit on an unvalidated tuple. The draft permits using an already validated tuple without repeating validation; do not claim a new path ID universally requires a new challenge. Defer expensive controller/history allocation until validation succeeds where permitted, while retaining enough bounded state to process validation and required control frames. Bound retries, idle validation, pending control frames, tombstones, retained ACK evidence and aggregate queued bytes. Rejected input must not manufacture a new full path context solely from an unauthenticated tuple or large ID.

BBR currently permits substantial bounded stores: 25,000 live delivery entries, 4,096 retained delivery entries and 32,768 recovery outcomes in the inspected source. Multiplying every maximum by path count can dominate the small path-registry cost. Establish aggregate as well as per-path limits, and measure idle, validated-backup, saturated and abandoned-path memory. Resource exhaustion must produce a controlled limit/decline/degradation outcome, never unbounded growth or silently corrupted delivery evidence.

## Maintenance and upstream relationship

The implementation forecast assumes the fork owns its extension and hand-ports necessary upstream fixes; it assigns no savings to upstream accepting multipath. That is a planning scenario, **not a change to accepted policy**. [ADR 0003](../adr/0003-follow-stable-upstream-releases.md) still bases releases on validated stable upstream releases, while [#651](https://github.com/the-sarge/quic-go-fast/issues/651) leaves the post-split relationship undecided. Accepting a permanent independent release policy requires reopening that ADR explicitly. Repository naming/detachment need not block design.

| Maintenance scenario | Expected work and planning allowance |
| --- | --- |
| Continue stable upstream integration | Reconcile a standing semantic diff across roughly 45–65 principal existing production files plus secondary sites, especially connection, ACK/loss, CID and crypto interfaces. For a narrow upstream patch, allow 1–3 focused review/validation sessions; for changes to recovery, migration or packet protection, allow 3–8 sessions and possible redesign. These are untested planning allowances, not observed rebase timings. A major representation change is not bounded by them. Re-run default-off and multipath interop on the merged revision. |
| Stop rebasing releases | Avoid repeated whole-tree merge resolution but own advisory monitoring, applicability analysis and security backports; Go `crypto/tls` QUIC-hook adaptation and compiler/platform changes; dependency updates; protocol interoperability; and native regression coverage. Name an owner and cadence through #651. Skipping upstream merges does not eliminate this work or retain automatic coverage from upstream's infrastructure. |
| Selectively adapt the Go reference | Preserve MIT/upstream attribution and provenance; port cohesive protocol logic/tests only after mapping local ownership and licensing. Its upstream v0.63.0 parent differs from this fork's base, and its Conn-driven send/scheduler choices conflict with our emission design. Reconcile each patch and run independent interop; source availability reduces discovery effort, not integration obligations. |

The estimates exclude unbounded maintenance research. Before committing to implementation, a bounded paper mapping of the reference's path/crypto/recovery changes should decide whether adapting those modules is cheaper than implementing from the specification with its tests as examples. No code import is authorized by this note.

## Consumer evidence and decision gates

[wiremux #1738](https://github.com/GridSwarm/wiremux/issues/1738) owns its layering/API decision and questions 20–21 about the first consumer and benefit. [wiremux #708](https://github.com/GridSwarm/wiremux/issues/708) owns the broader multipath motivation. GridCast's rateless DATAGRAM distribution is a plausible first aggregation consumer, while a general QUIC application can exercise backup continuity without wiremux. Neither is designated as the committed first adopter here.

The transport can supply a controlled test fixture first. Ask the consumer work to select its unique-useful-delivery boundary and acceptance thresholds, then compare the same sockets/paths and total offered load across: existing single-active-path migration, multiple independent connections/Wires, and one multipath connection. Include distinct-symbol delivery, time to resume useful delivery and time to restore a validated backup after a path failure, duplication/repair overhead, CPU per useful byte, memory, control latency and shared-bottleneck coexistence. A throughput sum alone cannot demonstrate benefit. Define noninferiority for the disabled/single-path profile separately. This is an evidence outline, not a campaign registration or a duplicate consumer benchmark contract.

Ordinary peers on an opted-in endpoint are a separate evidence population from default-disabled transports and negotiated multipath. Before public support, D0 must select acceptable throughput, tail send/control latency and CPU-per-useful-byte costs for that population; this is not an assumed zero-overhead requirement or a measured regression. Use a matched unregistered ordinary-only control, then compare ordinary-only and mixed ordinary/multipath traffic on opted-in qualified endpoints, including bulk producers and stateless-response pressure. Cover STREAM and DATAGRAM, GSO/batching and qualified fallback. Hold sockets, offered load, budget B, resource caps, Go/OS revision and acceleration settings explicit, and report queue/deadline/drop rates, memory and per-participant progress. Correctness gates include no connection close or path retirement solely from local timeout, bounded memory, and no starvation under the declared finite-participant/native-progress assumptions. Keep default-disabled equivalence and consumer multipath-benefit evidence separate. Fixtures and accounting support belong to the forecast; campaign execution remains separately budgeted, and none is claimed here.

Proceed to an implementation handoff only after the owner accepts the remaining product/interface choices, a protocol/interop pin and its gaps are understood, the Q2 sequence is explicit, resource accounting has a bounded design, and independent review finds the proposed ownership model credible. Finish the source-adaptation comparison and bounded-I/O feasibility/qualification plan before freezing estimates or slice boundaries. The owner-directed bounded-native-I/O and nonfatal local-backpressure decisions are incorporated; the mechanism, parameters and other choices below remain proposals for D0, not implementation authority:

| Decision for D0 | Proposed direction / consequence |
| --- | --- |
| First supported profile | QUIC v1, Reno, qualified exact native UDP transports with explicit bounded-write authority, conservative primary/backup. Reject external callbacks, managed/custom wrappers, BBR until M6, restricted transport/QoS combinations and unqualified platforms. Original server transport only. |
| Migration and handle model | Shared `Path` with mode errors and an error-bearing ID accessor; client same-ID local-socket migration and equal effective CID lengths on target transports. Two protocol-path slots; one validation candidate per path, two total, with one local operation at a time. Different-remote replacement can temporarily reduce redundancy. |
| Transport release and submission progress | Owner-directed bounded native send completion; proposed endpoint coordinator, finite positive B, exclusive deadline authority and all-send coverage. Freeze default/tolerance/resource limits and accept the proposed Transport.WaitMultipathIOStoppedV1 join that returns write authority after Close. `WaitTransportDetachedV1` still waits for all this connection's uses, close-race serialization and retained routing; local I/O bounds do not bound peer-dependent replacement or detachment. |
| Resource and CID policy | Initial grant 1 for the two-path profile; no additional unused-ID pre-grant at full capacity. Fence-pending retirement holds its slot; replenishment follows safe transfer into a separately budgeted retention allowance and both peers' credit/CID exchange. Accept measured aggregate byte/count and validation-candidate budgets, plus endpoint participant/readiness, completion, diagnostic, control and capacity-grant allowances. |
| Evidence and interop | Early complete private smoke checkpoint and required Linux peer job before public support. Known zero-limit oracle gap stays explicit. Choose acceptable ordinary-peer throughput/latency/CPU costs on an opted-in endpoint separately from default-disabled equivalence, and qualify mixed-load fairness, local-timeout survival and bounded memory. |
| Consumer benefit timing | Prefer allowing an exploratory implementation decision on general-replacement grounds, with meaningful comparative benefit and default-profile noninferiority required before recommending adoption. Owner may instead require a current-code migration/multiple-connection baseline before handoff. Either choice must be recorded; no experiment is dispatched here. |
| Q2 and maintenance | Prefer a pinned/completed Q2 baseline before core multipath merges. Keep both maintenance branches open; full sizing uses the hand-port scenario and does not amend ADR 0003. Accept the source-adaptation mapping before fixing slice boundaries. |

The benefit-timing recommendation does not establish that multipath beats existing migration or multiple connections; current-code baselines alone cannot do so. The later comparison requires the multipath candidate and the same resource/workload accounting, with consumer semantics owned by wiremux #1738/#708. A consumer requiring excluded authorization, QoS or exact-symbol steering can require a different scope or justify declining this first profile.

Reasons to decide against implementation include: no consumer benefit beyond separate connections at comparable resource cost; inability to obtain independent interoperability evidence; unacceptable regression or memory cost in the default profile; unwillingness to own crypto/recovery divergence; or a required public scheduling/authorization interface that cannot preserve accepted contracts. Record the specific reason and a revisit trigger, such as a measured unmet consumer need, upstream support, a compatible independent peer, or an accepted maintenance owner. An unfavorable comparison is a valid outcome of #646.
